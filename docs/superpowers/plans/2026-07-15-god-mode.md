# God Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Secret words typed into the ⌘K palette reveal a hidden Developer nav section and tint the nav — a visibility toggle backed by the existing `devtools` permission, with the words held server-side.

**Architecture:** A tiny schema-hidden endpoint (`POST /devtools/unlock`) compares the submitted text against `SS_GOD_MODE_WORDS` and returns the nav colour only to an actor who genuinely holds `devtools`; every other case returns an identical 404. The portal keeps god mode in memory on `AuthContext`, hooks the palette's currently-dead "Enter with no results" path, and adds one predicate (`godOnly`) to the nav/palette filters.

**Tech Stack:** FastAPI (async), pydantic-settings, pytest; React 18 + TypeScript + Vite, vitest.

**Spec:** `docs/superpowers/specs/2026-07-15-god-mode-design.md` — read it first.

## Global Constraints

- Branch: `feature/god-mode`. API tests: `cd api && .venv/bin/pytest tests/ -q` (**~50 seconds**, baseline **181 passing**). Portal: `cd portal && npm run build && npm test` (build ~1-2 min, vitest baseline **64 passing**). Run everything in the FOREGROUND — never background a command and never wait for a "monitor" notification; none exists.
- **God mode reveals, never grants.** The server enforces `devtools` on every request regardless. No client-side state may ever influence server authorisation.
- **The words never reach the browser.** Root `.env`, `SS_` prefix only. A `VITE_*` var would be inlined into the JS bundle and greppable — that is the one thing this design exists to avoid.
- **Every failure is byte-identical:** wrong word, correct word from a non-developer, and no-words-configured all return `404 {"code": "not_found"}`. No response may vary by reason.
- Errors are always `HTTPException(status_code=…, detail={"code": "<snake_case>"})`.
- Audit rows use the existing `audit()` service and must be added **before** the `db.commit()` that persists them, in the same transaction. Never store word material.
- No dev-DB seeding. No rate limiting or lockout (guessing grants nothing — see spec §1).
- Commit after every task with the message given in its final step.

```python
# api/src/serversherpa/api/routes/devtools.py
"""God mode — reveals the developer nav section.

This is a VISIBILITY toggle, not a permission. The server enforces the
`devtools` permission on every request regardless of god-mode state, so
guessing a word grants nothing: a non-developer who types the correct word
gets the same 404 as someone typing gibberish. That property is why this
needs no rate limiting — there is nothing behind the door to force.

The words live in SS_GOD_MODE_WORDS (server-side). A VITE_* equivalent
would be inlined into the portal bundle and readable from devtools.
"""

import secrets

from fastapi import APIRouter, HTTPException

from serversherpa.api.deps import CurrentUser, DbSession
from serversherpa.api.schemas import GodModeIn
from serversherpa.config import get_settings
from serversherpa.services.audit import audit

router = APIRouter(prefix="/devtools", tags=["devtools"])

# One refusal for every reason — wrong word, right word from a non-developer,
# feature unconfigured. Any variance between them is the leak this avoids.
_REFUSED = HTTPException(status_code=404, detail={"code": "not_found"})


def _word_matches(candidate: str) -> bool:
    words = [w.strip() for w in get_settings().god_mode_words.split(",") if w.strip()]
    # compare_digest on every configured word; `any()` short-circuits but the
    # timing tells an attacker nothing they could use (see module docstring).
    return any(secrets.compare_digest(candidate, w) for w in words)


@router.post("/unlock", include_in_schema=False)
async def unlock(body: GodModeIn, user: CurrentUser, db: DbSession) -> dict:
    if not _word_matches(body.word) or not user.access.can("devtools", "view"):
        raise _REFUSED
    audit(db, actor_id=user.person.id, entity_type="auth",
          entity_id=str(user.person.id), action="godmode.enable")
    await db.commit()
    return {"nav_color": get_settings().god_mode_nav_color}
```

```ts
// portal/src/lib/godmode.ts
/** God mode reveals; it never grants. An item needs BOTH its permission and
 *  — when flagged godOnly — an active god mode. The server enforces the
 *  permission on every request regardless of what the nav chooses to show. */

export interface GodGatedItem {
  resource: string;
  godOnly?: boolean;
}

export function isNavItemVisible(
  item: GodGatedItem,
  can: (resource: string, action: 'view') => boolean,
  godMode: boolean,
): boolean {
  if (!can(item.resource, 'view')) return false;
  return !item.godOnly || godMode;
}
```

```ts
/** Returns the nav colour on success, or null when refused. A refusal is
 *  indistinguishable from a wrong word by design — the caller must not
 *  surface it, or it becomes the signal the 404 exists to avoid. */
export async function unlockGodMode(word: string): Promise<string | null> {
  const resp = await apiFetch('/devtools/unlock', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ word }),
  });
  if (!resp.ok) return null;
  const data: { nav_color: string } = await resp.json();
  return data.nav_color;
}
```
