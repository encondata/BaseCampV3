# Wiki Phase 2 (collaboration) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add comments (inline + page threads) with @mentions, page templates, watching with inbox
notifications, and reviews/approvals with periodic review reminders to the wiki built in Phase 1.

**Architecture:** New tables in migration 0075; API modules under `serversherpa/wiki/` and
`api/routes/wiki/`; one notification fan-out service that every event goes through and that uses the
existing portal inbox (`notifications.inbox.notify`); Tiptap schema gains `mention` (node) and
`commentThread` (mark), kept DOM-free so the server renderer stays in parity; the wiki SPA gains a
comments rail, template picker/management, watch controls and a reviews queue.

**Tech Stack:** as Phase 1 (FastAPI/SQLAlchemy/Alembic/Postgres; React 18/Vite 5/Tiptap 2.27/Hocuspocus 2.15; vitest 3).

**Spec:** `docs/superpowers/specs/2026-09-25-wiki-design.md` §7 (and §3 for permissions).
**Phase 1 plan (conventions, API contract):** `docs/superpowers/plans/2026-09-25-wiki-phase1.md`.

## Global Constraints

- Everything in the Phase 1 plan's Global Constraints still applies (worktree `.claude/worktrees/wiki`, branch `wiki`, `PYTHONPATH=$PWD/api/src`, `SS_TEST_DB=serversherpa_test_wiki`, foreground suites, no full API suite in tasks, American English, 404-not-403, audit every write, commit trailer `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`).
- Migration **0075** (`down_revision = "0074"`), one migration for all Phase 2 schema.
- Space settings keys become allowed (in `serversherpa/wiki/space_settings.py` ONLY): `readers_can_comment: bool` (default true), `require_approval: bool` (default false), `review_interval_months: int | None` (1–60 or null). A reader of a missing key gets the default via one helper `space_setting(space, key)`.
- All inbox notifications go through ONE service, `serversherpa/wiki/notify.py`, which calls `notifications.inbox.notify(db, person_id, kind, title, body=, link=, payload=)`. Kinds: `wiki_mention`, `wiki_update`, `wiki_comment`, `wiki_review_request`, `wiki_review_decision`, `wiki_review_due`. `link` is the absolute wiki URL `f"{settings.wiki_origin}/n/{node_id}"` (+ `#comment-<id>` for comments). Never notify the actor; never notify someone who can't view the node at send time (evaluate with the Phase 1 `AccessIndex` built from that person's principal via `principal_from_access(resolve_access(db, person_id))`); de-duplicate recipients per event (a mentioned watcher gets only the mention).
- Principal-for-person-id: reuse the helper Phase 1's `/wiki/internal/collab/level` uses — do not write a second one.
- The portal must open absolute (http/https) inbox links with `window.location.assign` (or a new tab), never `navigate()` — relative links keep today's behavior.
- Mention and comment bodies are plain text + mention ids (`{"text": str, "mentions": [uuid]}`), rendered as text; never HTML.

### Task 2: Notification fan-out + watches API

**Files:** create `wiki/notify.py`, `api/routes/wiki/watches.py`; modify routes that emit events (pages publish, nodes create/copy/upload-complete); portal inbox link handling (find the inbox list/popover and ToastHost default `openLink` in `portal/src/components/`); tests `test_wiki_notify.py`, `test_wiki_watches_api.py`, portal tests for absolute links.

```python
# wiki/notify.py
async def recipients_who_can_view(db, node: WikiNode, person_ids: Iterable[uuid.UUID]) -> set[uuid.UUID]
async def watchers_for(db, node: WikiNode) -> set[uuid.UUID]          # node + ancestors (path) + space
async def auto_watch(db, person_id, node_id) -> None                  # idempotent
async def on_published(db, node, *, actor_id, version) -> None        # wiki_update to watchers
async def on_created(db, node, *, actor_id) -> None                   # wiki_update to watchers of ancestors/space
async def on_comment(db, node, comment, *, actor_id) -> None          # wiki_comment to watchers + thread participants; mentions handled separately
async def on_mentions(db, node, person_ids, *, actor_id, context: str, link_suffix: str = "") -> None  # wiki_mention
async def on_review_requested / on_review_decided / on_review_due(...)
```
Routes: `GET /wiki/watches` (mine, with node/space titles, only viewable), `PUT /wiki/watches {node_id|space_id}` (view level), `DELETE /wiki/watches/{id}` (own only), `GET /wiki/nodes/{id}/watch` → `{watching: bool, via: 'node'|'ancestor'|'space'|null}`.
Behavior: creating or publishing a page auto-watches the actor; publish → `on_published`; node create (page/folder/file incl. upload complete, copy root) → `on_created`. Notification titles: `"<actor> published <title>"`, `"<actor> added <title> to <parent or space>"`.
Tests: fan-out excludes actor, non-viewers (a watcher whose access was removed gets nothing), duplicates; ancestor and space watches; auto-watch; watches API permissions; portal absolute-link test.

### Task 3: Comments + mentions API

**Files:** create `wiki/comments.py`, `api/routes/wiki/comments.py`; modify `wiki/content.py` (`mention_ids(doc) -> set[str]`), `wiki/pages.py` publish (mention notifications for ids new since the previous published version); tests `test_wiki_comments_api.py`, `test_wiki_mentions.py`.

Routes: `GET /wiki/nodes/{id}/comments` → threads `[{thread_id, anchor, resolved_at, resolved_by, comments:[CommentOut]}]` (view); `POST /wiki/nodes/{id}/comments {body, thread_id?, anchor?: bool}` (new thread when no thread_id; permission: edit, or view when `readers_can_comment`); `PATCH /wiki/comments/{id} {body}` (author only); `DELETE /wiki/comments/{id}` (author or manage; soft delete, body hidden as "Comment deleted"); `POST /wiki/comments/threads/{thread_id}/resolve` / `reopen` (edit, or thread author); `GET /wiki/nodes/{id}/mentionable?q=` → `[{id, name}]` people (with accounts) who can view the node, name/email ILIKE, max 10 (view level).
`CommentOut {id, thread_id, parent_id, body:{text, mentions:[{id,name}]}, author: PersonRef|null, created_at, edited_at, deleted: bool}`. Body text 1–5000 chars; mentions must be people who can view the node (others dropped silently); mention notify on post and on edit (only newly added ids). `on_comment` for watchers and earlier thread participants.
Publish: `mention_ids(new) - mention_ids(previous published)` → `on_mentions(context='page')`.
Tests: permissions matrix (readers_can_comment on/off), threads/replies ordering, edit/delete own, resolve/reopen, orphan-safe (anchor thread whose mark was deleted still listed), mention filtering + notifications, publish mention diff, audit rows.

### Task 5: Reviews/approvals + periodic review + reminders

**Files:** create `wiki/reviews.py`, `api/routes/wiki/reviews.py`; modify `wiki/pages.py` publish, `wiki/worker.py` (daily `reminders` job scheduling + handler); tests `test_wiki_reviews_api.py`, `test_wiki_review_reminders.py`.

Rules:
- If the page's space has `require_approval` and the caller is not a manager of the page → `POST /pages/{id}/publish` returns 409 `review_required`. Managers publish directly (approval is theirs to give).
- `POST /wiki/pages/{id}/reviews {note?}` (edit): snapshot current draft as a `submitted` version, create a pending review (replacing an existing pending one → that one becomes `withdrawn`), notify approvers (manage-level holders of the page, resolved from effective grants: persons directly, plus members of roles/groups/clients/partners — cap the fan-out at 200 with a log line) via `on_review_requested`.
- `GET /wiki/reviews?status=pending&mine=approver|requester` → list with node title/space, requester, created_at (only pages the caller can view; `approver` = pages the caller manages).
- `GET /wiki/reviews/{id}` → review + `submitted` version content + current published content (for the diff).
- `POST /wiki/reviews/{id}/approve {note?}` (manage): publish exactly the submitted snapshot (new `published` version copying its content; `has_unpublished_changes` recomputed vs draft), status approved, `on_review_decided`; `POST /wiki/reviews/{id}/reject {note}` (manage; note required) status rejected, notify requester; `POST /wiki/reviews/{id}/withdraw` (requester or manage).
- Periodic review: on publish/approve, if `review_interval_months` (page, else space setting) set → `next_review_at = now + interval`; `PATCH /wiki/nodes/{id}` accepts `review_interval_months` (manage; null clears); `POST /wiki/pages/{id}/mark-reviewed` (edit) → last_reviewed_*, next_review_at advanced; `GET /wiki/spaces/{key}/due-reviews` → pages with next_review_at ≤ now + 14 days, ordered.
- NodeOut gains `review: {interval_months, next_review_at, last_reviewed_at, state: 'ok'|'due_soon'|'overdue'|null, pending_review_id|null}` for pages (due_soon = within 14 days). Update the TS types.
- Worker: once per day (and at startup if the last run is > 24 h old; persist last run as a `reminders` job row), notify page owners for pages with `next_review_at ≤ now` and `review_notified_for IS DISTINCT FROM next_review_at` (`wiki_review_due`), then set `review_notified_for`.
Tests: review_required gate; manager direct publish; submit/replace/withdraw; approve publishes the snapshot even if the draft moved on; reject needs note; approver fan-out; due-review computation; reminders once per due date; NodeOut review block.

### Task 7: Comments UI

**Files:** create `wiki/web/src/comments/{CommentsRail,Thread,CommentComposer,commentsStore}.tsx|ts` (+ tests); modify `PageView.tsx`, `SelectionBubble.tsx` ("Comment" action), `wiki.css`.
- Right rail toggles between Contents and Comments (count badge). Threads ordered by document position (inline, by the first mark occurrence) then page threads by date; resolved threads collapsed under "Resolved (n)"; orphaned inline threads (mark gone) listed under "Detached".
- Selecting text → bubble "Comment" → composer; for editors, posting creates an inline thread (`anchor: true`) and then applies the `commentThread` mark with the new thread id to the selection. Viewers with commenting rights can't write the document, so their selection comment becomes a page-level thread whose first comment starts with the quoted selected text (`> "…"`).
- Clicking a highlighted mark focuses its thread and vice versa (scroll + highlight).
- Composer: plain textarea with `@` mention picker (mentionable endpoint), Cmd/Ctrl+Enter posts; edit/delete own; resolve/reopen.
- Polling every 20 s while the rail is open (no websockets in Phase 2).
- Deep link `#comment-<id>` opens the rail and focuses that comment.
