# Kiosk (web mode): framework, sign-in, and shell

The kiosk is the scanning-floor face of ServerSherpa. It will eventually run in four modes (Web only, Laptop Mode, RFID Middleware, Device App). This spec builds the framework and the web mode's sign-in and shell only: a second app in `kiosk/` that mirrors the portal's look, signs in three ways (email and password, link with phone, move password placeholder), registers itself as a kiosk Device, and ships as its own Docker image on its own port. No scanning.

**Date:** 2026-09-13 · **Status:** approved (Jimmy, 2026-09-13: "looks good lets go") · **Branch:** `kiosk-web` (worktree off `reports`)

## Decisions already made

| Question | Decision |
|---|---|
| Code sharing | Own app in `kiosk/`; a Vite alias `@portal` reaches into `portal/src` for **stylesheets and React-free TypeScript only**. No npm workspace, no copied tokens. |
| Session model | Same cookie model as the portal (`ss_refresh` httpOnly cookie on the API host, in-memory access token). No body refresh tokens. |
| Who may sign in | New permission resource `kiosk` with one action `view`. Granted by default to developer, founder, super_admin, admin, staff, worker. |
| Kiosk identity | Each kiosk self-registers as a `Device` row (`device_type='kiosk'`) by serial, using the signed-in user's session. No pre-shared secret, no device token. Signing in registers the kiosk automatically (30 days, renewed when expired or within 7 days of expiring); anyone allowed to use the kiosk can do it. Register/Renew remain available in the portal, for registering ahead of time or renewing a kiosk nobody has signed into. |
| Pairing transport | Kiosk polls every 2 s while a code is showing. No WebSocket or SSE. |

### Runtime config (`src/lib/config.ts`)

Resolution order, read per call (never at module scope, same reason as the portal's `apiUrl()`):

1. `window.__KIOSK_CONFIG__.apiUrl` / `.portalUrl` (written by the Docker entrypoint, empty object in dev)
2. `import.meta.env.VITE_API_URL` / `VITE_PORTAL_URL`
3. `http://${window.location.hostname}:8000` / `http://${window.location.hostname}:5173`

`kioskVersion()` returns `import.meta.env.VITE_KIOSK_VERSION ?? package.json version` (Vite `define`).

### Identity (`src/lib/identity.ts`)

- `serial`: localStorage `ss.kiosk.serial`; generated once as `kiosk-web-<uuid4>`.
- `name`: localStorage `ss.kiosk.name`; default `Kiosk <last 4 hex of serial, uppercase>`; editable in Kiosk settings (trimmed, 1–80 chars, required).
- `getIdentity()` returns `{ serial, name }`. Both reads are wrapped in try/catch; if storage is unavailable the serial is regenerated per page load and settings shows a warning "This browser can't remember kiosk settings".

### Transport (`src/lib/api.ts`)

A compact re-implementation of the portal's session behavior, not an import of `portal/src/lib/api.ts` (that file drags in 500 lines of portal endpoints and its `apiUrl()` ignores runtime config). Same rules, stated once here so tests can pin them:

- Access token in a module variable only. Never in storage.
- `refreshSession()` is single-flight; `POST {api}/auth/refresh` with `credentials: 'include'`, no Authorization header; null on failure.
- `apiFetch(path, init)` pre-refreshes when the token is within 30 s of expiry, attaches `Authorization: Bearer`, and on 401 performs exactly one refresh and retry, then calls `notifySessionEnded()`.
- `loginRequest(email, password)` → `POST /auth/login` with body `{email, password, client: "kiosk"}`.
- `logoutRequest()` → `POST /auth/logout`, never throws.
- `createPairRequest({serial, name})`, `pollPair(code, pollToken)`, `heartbeatRequest(body)` — see API.
- `ApiError { status, code }` mirrors the portal's; `code` comes from `detail.code`, falling back to `'network'`.
- Types `SessionData`, `PersonOut`, `UiPreferences` are imported (type-only) from `@portal/lib/api`; `computeCan` from `@portal/lib/access`; `applyPreferences` from `@portal/lib/settings`.

### Auth context (`src/auth/KioskAuthContext.tsx`)

State: `status: 'loading' | 'authed' | 'anon'`, `person`, `perms`, `mustChangePassword`, `registration: RegistrationState | null` (from heartbeat), `sessionExpiresAt`.

- On mount: `refreshSession()`; if it returns a session → `adopt(session)`; else `anon`.
- `adopt(session)`: store token, `applyPreferences(session.preferences)`, set state, start the heartbeat.
- `login(email, password)` → `loginRequest` → `adopt`. `completePair(session)` → `adopt` (called by PairPanel).
- `logout()` → stop heartbeat, `logoutRequest`, clear state, `anon`.
- Subscribes to `onSessionEnded` → same as logout without the request.
- Subscribes to `installVisibilityRefresh` (refresh on tab focus), same as the portal.

### Heartbeat (`src/lib/heartbeat.ts`)

`startHeartbeat(onState, intervalMs, firstBeatIsSignIn)` posts immediately, then every 60 s, `{serial, name, mode, version}` to `POST /kiosk/heartbeat`; calls `onState(response.registration)` on success; on any failure (network, 423 read-only, 403) it keeps the last known state and retries next tick. Returns a `stop()` that clears the timer. It also re-posts immediately when the kiosk name changes (settings page calls `heartbeatNow()`). When `firstBeatIsSignIn` is true (set by `KioskAuthContext` only for the beat that follows `login()`/`completePair()`, never a cookie restore), that one beat only adds `sign_in: true` to the body — see the API's `### Heartbeat` section below for what the server does with it.

- `.kiosk-main`: the routed page in a `.portal-page`.
- `.kiosk-foot`: a one-line mono status bar, the shell's third grid row (`.portal-shell.kiosk-shell` is `grid-template-rows: auto minmax(0, 1fr) auto`), items separated by a `·` (`.kiosk-foot-sep`): Kiosk name, Mode, Version, and — signed in only — Signed in as, Session ends (local time via `toLocaleString()`), Registration (`Checking…` while `registration` is still null). Signed out (the Settings page when anon) it shows only Kiosk, Mode, and Version.

No side nav, no command palette, no notifications panel. The kiosk is full-width.

**Home (`/`)** is launcher-only: eyebrow, title, and the feature tiles. The kiosk identity facts that once lived on Home now live in the shell's `.kiosk-foot` footer, visible from every screen.

**WebUSB needs Chrome or Edge on a secure origin** (https or localhost) — worth stating because the kiosk often runs on a tablet. **No hardware was tested.** There is no physical Zebra on this machine and WebUSB cannot be driven from browser automation, so the ported ZPL, the `^HH` round-trips, and printing itself are covered only by the ported unit tests and by a fake USB device injected in the live browser. **Factory Reset (2026-09-14).** Jimmy: "Add an extra option to the page to perform a factory reset on the printer and run through a full setup afterwards." A fourth tool row, after Full Printer Setup and before the disabled Install Fonts: **Factory Reset** ("Restore the printer's factory defaults, then set it up again." / "Reset printer"), gated on a connected printer like the other two and styled destructively (`btn-solid btn-danger`, the red already in `directory.css`). It opens `FactoryResetModal` — the same `modal-scrim` / `rgm-card` shell, eyebrow "Printer", title "Factory reset", with `rgm-*` step markers Confirm → Reset → Setup.

1. **Confirm** names the printer (product name, plus model/firmware/DPI from `~HI` when known) so nobody wipes the wrong one, warns that all configuration, saved offsets and stored settings are lost and that the printer restarts, and offers a checkbox "Calibrate the media after the reset (feeds a label or two)" — **default on**, because factory defaults wipe the media calibration. Cancel is a `mini-btn` and carries the autofocus; the destructive "Factory reset" is last and is never focused, so a stray Enter on the open modal cannot wipe a printer.
2. **Reset** runs a step list with per-step state (pending / running / done / failed): *Sending factory defaults* (`^XA^JUF^XZ`), *Waiting for the printer to restart*, *Calibrating media* (`~JC` then `waitForPrinterIdle`, only when the box was checked), *Saving settings* (`^XA^JUS^XZ`), *Reading configuration* (`^XA^HH^XZ` + `parseConfiguration`). Every command goes through the hook, so it all lands in the page's command log.
3. **Setup** — on success the modal closes and the existing `PrinterSetupModal` opens **seeded** with that post-reset configuration (new optional `initialConfig` prop; absent, it reads the printer itself as before) and an `intro` eyebrow "Printers · After factory reset". The wizard is not duplicated.

**The restart poll** is the awkward part: `^JUF` reboots the printer, which drops off USB for a few seconds. The step calls `ensureOpen()` (new on `useZebraPrinter`: reopen and re-claim the held device, and deliberately **not** a connection drop, so a caller polling a rebooting printer can retry) before each attempt, then `~HI`, every 2 s for up to 45 s. A thrown transfer error — or a handle that will not reopen yet — means "not back yet" and polling continues. Timing out fails the step with "The printer did not come back. Power-cycle it, reconnect, and try again."; a failure offers **Try again** (re-runs from the failed step, not from the start — the defaults are not sent twice) and **Close**. If the hook has given up the device handle entirely, the message is "Reconnect the printer to finish setup." and only Close is offered, so the operator lands back on the card and can press Connect again rather than sitting in a dead modal.

**Destructive, and recorded in the portal (2026-09-14).** The reset itself is still pure WebUSB, but when the run ends the modal posts it to **`POST /kiosk/printer-events`** (`kiosk:view`; body `{serial, event: "factory_reset", outcome: "completed" | "failed", printer_model, printer_firmware, calibrated, failed_step, error}`; 404 `device_not_found` for a serial that is not a kiosk; 204). The endpoint writes exactly one audit row against that kiosk's Device — `entity_type="device"`, `action="kiosk_printer_factory_reset"`, the signed-in actor, the client IP, and the body's fields as `changes` with the null ones omitted — and stamps `last_seen_at`. That row is what the portal's **/audit** page shows (labeled "Printer factory reset", with the kiosk's name in the Target column now that `entity_refs` resolves `device`) and, since `/auth/me/activity` reads the same `audit_log`, it also lands in the actor's own history. `event` is an enum with one member so later printer maintenance becomes another member, not another endpoint.

**Failures are recorded too** — a reset that left a printer stuck halfway is exactly the run an admin wants to find later — carrying the step it died on and the message the operator saw. The report is best-effort and can never break the reset: `postPrinterEvent` resolves to a boolean instead of throwing, it is fired and never awaited, and the modal only shows a small line ("Recorded in the portal." or, on failure, "Couldn't record this reset in the portal — tell an admin.") while the hand-off into the setup wizard proceeds regardless.

**Read-only mode does NOT block it** (`/kiosk/printer-events` is in `READ_ONLY_EXEMPT_PATHS`): the physical reset already happened out in the warehouse, and refusing to record it during a maintenance freeze would not undo it — it would only lose the trail the feature exists to create — while an append-only audit row is safe to write while frozen. That is a deliberate difference from `/kiosk/scans` and `/kiosk/timeclock/*`, which stay frozen because their writes are real data the kiosk can hold and retry once the freeze lifts. It is not inherited into the temp-password exempt set.

- **Modal height on a kiosk screen.** `printers.css` gives the alignment and setup cards `max-height: none; overflow: visible` so the portal's dropdowns can escape the card. A kiosk is often a tablet in landscape (~640px tall), where that drops the footer's Next/Finish buttons off the bottom of the fixed scrim. `kiosk.css` caps both cards to `92dvh` and scrolls the body instead, using the portal's full four-class chain because a shorter selector loses to its `max-height: none`.

A tab registry (`src/lib/settingsTabs.ts`) lists six sections in order: Appearance ("Theme, accent, and text size for this kiosk."), Sound ("Scan and alert sounds."), Devices ("Scanners, printers, and readers attached to this kiosk."), This Kiosk ("This kiosk's name, identity, and connection.", `anon: true`), Admin ("Kiosk administration.", `requires: 'admin'`), and Developer ("Diagnostics and developer tools.", `requires: 'developer'`). `visibleTabs(tabs, {isAdmin, isDeveloper, signedIn})` drops a tab whose `requires` the signed-in person lacks; signed out, only tabs carrying `anon` survive, which today means This Kiosk alone — **gating is by visibility only: a hidden tab is never rendered, never shown disabled**, and it carries no trace in the DOM (no "Admin"/"Developer" text for a worker, no "Appearance"/"Sound"/"Devices"/"Admin"/"Developer" text signed out). Gating rule: Admin needs `max_rank >= ADMIN_RANK` (60, from `@portal/lib/access`); Developer needs `'developer'` in the session's `roles`. `KioskAuthContext` derives both (`isAdmin`, `isDeveloper`) from `SessionData.max_rank` / `.roles` (`0` / `[]` when anon, so both are `false` signed out); `Settings.tsx` itself reads `status` to compute `signedIn`.

The page renders a `.segmented.settings-tabs` tab strip (the same `role="tablist"` pattern as the portal's directory pills) built only from the visible tabs. The active tab lives in the `tab` search param (`useSearchParams`) so it survives a reload and can be deep-linked; an unknown or currently-hidden `tab` value (e.g. a worker hitting `?tab=admin`, or anyone signed out) falls back to the first visible tab — Appearance signed in, This Kiosk signed out. Every tab body but This Kiosk's is a placeholder for now: the tab's label as an `h2.settings-tab-title`, its blurb as `.page-hint`, and a `.kiosk-placeholder` card reading "This section is not available yet." This Kiosk instead renders `<ThisKioskPanel />` and no placeholder card.

Developer tab: the first control is a Developer mode toggle (kiosk-local, localStorage `ss.kiosk.devMode`, footer shows "Dev mode On"); what it reveals is defined per feature as they land — today it only flips the flag.

**Local data inspector (2026-09-13):** at the bottom of the Developer tab body — after the dev-mode switch, setup-state selector, and Local data row above, and visible whenever the Developer tab is (no dev-mode gate, unlike those three) — `src/components/LocalDataInspector.tsx` renders three collapsible `<details className="local-section">` sections reading straight out of `localDb.ts`: Assets (`getAll('assets')`), People (`getAll('people')`), and Sync metadata (`readMeta('sync')`). Assets columns: Asset ID, Name, RFID, Serial, Make / Model, and a `mini-btn` "Label" per row that toggles an inline row below it showing that asset's `label` placeholder map as a `.local-kv` key/value list. People columns: Name, RFID tag, ID (mono, first 8 characters, full id in `title`), and Flags (`chip tag` "worker"/"account" when `is_worker`/`has_account`). CSS lives in `kiosk.css`: `.local-section` (+ `> summary` with the ▸/▾ marker), `.local-toolbar`, `.local-count`, `.local-table`(-wrap) and its `th`/`td`/`.mono`, `.local-kv`.

**Appearance tab — Flash duration (2026-09-14):** a third `.settings-row` below the two color pickers, label "Flash duration", hint "How long the screen flashes after a scan.", holding a range (`aria-label="Flash duration"`, min 100, max 2000, step 50) and a mono readout ("350 ms"). It writes `flash_ms` into the same kiosk-local `ss.kiosk.appearance` record (default **350**, clamped to 100–2000 on both read and write, so a hand-edited file can never hand the overlay a 0 ms flash), and `Scan.tsx` passes it to `flash(color, ms)` on both the match and the no-match path. `flash()`'s own default stays 350 for any caller that doesn't care.

**Sound tab (2026-09-14):** what this kiosk plays on a scan, kiosk-local in `ss.kiosk.sound` (`lib/sound.ts`, the same store/hook idiom as `appearance.ts`): `{good, not_found, volume}` where each choice is `{kind:'none'} | {kind:'builtin', id} | {kind:'upload', id}` and `volume` is 0–1 (default **0.8**, clamped). Defaults: good `builtin:chime`, not-found `builtin:buzz`. Built-ins are **synthesized with the Web Audio API**, not shipped as files — nothing to cache, nothing to 404 on an offline kiosk: `chime` (two rising sine notes, ~180 ms), `beep` (880 Hz square, 120 ms), `double_beep`, `buzz` (150 Hz sawtooth, 300 ms) and `bonk` (a descending sine). One `AudioContext` is created lazily on the first play and shared; the first play always follows a user gesture (a scan is a keypress), and `resume()` is called anyway for browsers that still start it suspended.

Uploads are the operator's own files, stored whole — `{id, name, type, size, blob, created_at}` — in IndexedDB **`sounds` (localDb v3**, keyPath `id`, deliberately outside `STORES` so "Clear local data" leaves them alone, like `outbox`). `addUploadedSound(file)` rejects `'not_audio'` for anything that isn't `audio/*` and `'too_large'` past **2 MB**; playback goes through an `HTMLAudioElement` over an object URL made once per id and revoked on removal, and `removeUploadedSound` resets any choice that pointed at the file to `none` so a scan never falls silent pointing at a row that no longer exists. `playScanSound('good' | 'not_found')` never throws — audio is feedback, never a gate.

The tab body (`components/SoundPanel.tsx`) is two `.settings-row`s, "Good scan sound" and "Not-found scan sound", each a native `<select>` (None, the built-ins, then the uploads under an "Uploaded" `optgroup`) with a "Play" `mini-btn` that previews the current choice — a native picker because the kiosk cannot import the portal's `ComboBox` across the two-Reacts boundary, and a sound is not something a label can describe. Then a "Volume" row (range 0–100 with a mono `%` readout) and an "Uploaded sounds" row: a file input (`accept="audio/*"`, helper text "MP3, WAV, or OGG up to 2 MB. Stored on this kiosk only.") over a `.sound-uploads` list of `.sound-upload-row`s (name, size in KB, Play, Remove). Rejections show inline as `.form-error`: "That file is too large (2 MB max)." / "That doesn't look like an audio file."

### Kiosk Setup wizard (2026-09-13)

The first real Kiosk Setup flow: a three-step wizard at `/setup` — pick a move, then which of that move's sites this kiosk is at, then a scan type — that stamps the kiosk's `Device` row server-side and marks `kiosk_setup_complete`. This replaces the earlier "Kiosk Setup is a placeholder" state (see "This Kiosk moves off /setup" above): `setup` drops `placeholder: true` in `features.ts` (it stays `alwaysAvailable`), and `/setup` moves from outside `KioskGuard` to inside it — setup writes a Device row on the signed-in person's behalf, so it now requires a signed-in person like every other feature route, while `featureAvailable` keeps it (and Settings) usable regardless of `kiosk_setup_complete`.

**Endpoints** (`api/src/serversherpa/api/routes/kiosk.py`, both `kiosk:view`):
- `GET /kiosk/setup-options` → `SetupOptionsOut {initiatives: [{id, name, status, status_label, client_name, scheduled_start, scheduled_end, source_site, destination_site}], scan_types: [{key, label, color}]}`. Initiatives are `initiative_type == 'move'`, `archived_at IS NULL`, and `status` **not** one of `HISTORICAL_INITIATIVE_STATUSES = ("completed", "cancelled")` — the terminal/historical keys from the `initiative` status vocabulary seeded in `migrations/versions/0016_initiatives.py` (the full vocabulary is `planned`/`scheduled`/`in_progress`/`on_hold`/`completed`/`cancelled`; everything but the last two is offered). This is broader than the portal's `DeviceEditModal.tsx`/`KioskDevices.tsx` move picker (planned/in_progress only) — the kiosk deliberately shows every move still in play, including `scheduled` and `on_hold`. `status_label` comes from that same vocabulary (falls back to the raw key if a value is ever missing); `client_name` is the move's `Client.name` (outer-joined on `client_id`, `null` when unset); `scheduled_start`/`scheduled_end` are the `Initiative` columns of the same names, as ISO strings (`null` when absent). `source_site`/`destination_site` are `{id, name} | null`, outer-joined from the move's `origin_site_id`/`destination_site_id` (either can be unset on a move that hasn't had its sites assigned yet). Ordering: in-progress moves first, then everything else, then by the earliest `scheduled_start` (nulls last), then by name. Scan types are active `asset` status values, ordered by `sort_order` then label. This endpoint exists because workers hold `kiosk:view` but not `initiatives:view` — they cannot call `/initiatives` directly, so the kiosk gets only the narrow slice it needs.
- `POST /kiosk/setup` body `KioskSetupIn {serial, initiative_id, site_id, scan_status}` → `KioskSetupOut {device_id, initiative_id, initiative_name, site_id, site_name, site_role, scan_status, scan_status_label}`. Finds the kiosk `Device` by serial (404 `device_not_found` if absent or not a kiosk), re-validates `initiative_id` against the same move/not-complete-or-historical/not-archived filter (422 `bad_initiative`) and `scan_status` against the active asset-status keys (422 `bad_scan_status`) — never trusts the options list a stale client cached — then checks `site_id` equals the chosen initiative's `origin_site_id` (`site_role = "source"`) or `destination_site_id` (`site_role = "destination"`), 422 `bad_site` otherwise. Sets `current_initiative_id`, `site_id`, `scan_status`, `updated_at`, and audits `action="kiosk_setup"` on `entity_type="device"` with `changes={initiative_id, site_id, scan_status}`. Not read-only exempt (it writes); 423 under read-only mode.

**Kiosk selection cache** (`src/lib/kioskSetup.ts`): `KioskSetupSelection {initiativeId, initiativeName, siteId, siteName, siteRole, scanStatus, scanLabel}`, kiosk-local, mirrors `devMode.ts`/`setupState.ts`'s store/hook shape (`readKioskSetup`/`writeKioskSetup`/`clearKioskSetup`/`subscribeKioskSetup`/`useKioskSetup`, localStorage key `ss.kiosk.setup`, same try/catch idiom). The server Device row is the source of truth; this is only a local cache of the display names (from the `/kiosk/setup` response) so the summary card and footer render without an extra fetch. `useSyncExternalStore` needs a referentially stable snapshot when nothing changed or it re-renders forever, so `read()` caches the parsed object against the raw string it came from rather than re-parsing every call.

**`pages/KioskSetup.tsx`**: eyebrow "Kiosk · Setup", title "Kiosk setup". With a saved selection and `kiosk_setup_complete === 'complete'`, shows a `.setup-summary` card ("This kiosk is set up for **{name}** at **{siteName}** ({siteRole}) · scan type **{label}**") with "Change setup" (`mini-btn`, re-enters the wizard at step 1 with all three fields pre-selected) and "Go to home" (`btn-solid`, → `/`). Otherwise a `.setup-wizard` with a `.setup-steps` indicator ("Step 1 of 3 · Move" / "Step 2 of 3 · Site" / "Step 3 of 3 · Scan type") and, per step, a `.setup-cards` grid (`grid-template-columns: repeat(auto-fit, minmax(240px, 1fr))`, dynamic like `.kiosk-launcher`) of tap-to-select `.setup-card` buttons (`role="option"`/`aria-selected`, mirroring `.kiosk-tile`) — no native `<select>`, and large touch targets matter more here than the portal `ComboBox`'s picker affordances anyway (which is a `.tsx` the kiosk cannot import across the two-Reacts boundary regardless). Step 1 ("Which move?") loads on mount via `getSetupOptions()` ("Loading moves…" while pending; a load failure shows `.form-error` "Couldn't load setup options." with a `mini-btn` Retry; an empty initiatives list shows "No active moves. Ask a coordinator to plan one."). Each move card shows its name, a status chip (`chip tag`, or `chip c-green` when `in_progress`) with `status_label`, a `.setup-card-meta` line for `client_name` when present, another for `scheduled_start`/`scheduled_end` when present (formatted short, e.g. "Sep 20 – Sep 25"), and a `.setup-card-sites` line "{source} → {destination}" (`—` for a missing side). ### Local move data (2026-09-13)

After Kiosk Setup saves, the kiosk downloads the selected move's data into a browser-stored database so it can recognize an asset or a person without the API.

**Endpoints** (`routes/kiosk.py`, both `kiosk:view`, both one response with no paging — the roster is hundreds to a few thousand rows, the people list a few hundred):
- `GET /kiosk/sync/assets?initiative_id=<uuid>` → `KioskAssetsSyncOut {initiative_id, initiative_name, generated_at, assets: [KioskAssetOut]}`, where `KioskAssetOut = {id, asset_id, name, rfid, serial_number, make, model, make_model, label}`. `asset_id`, `make`, `model`, and `make_model` are computed straight from the asset/model columns (same join rule as `values.py`, `asset_id` = `Asset.legacy_id`, the human Asset ID; `rfid` is `Asset.rfid_tag`) — **not** read out of `label`, so an admin deactivating or deleting those placeholders (or the whole catalog) never breaks the endpoint's own fields. The roster is `initiative_assets` joined to `assets` (+ outer-joined `asset_models`), ordered by `legacy_id`; an asset not on the roster is never returned, but an *archived* asset that is still on the roster is returned like any other — roster membership is the truth here, not `archived_at`. `label` is the **label placeholder map** for that asset on that move, built by the label generator's own `labels/generate/values.py::placeholder_values()` over the *active* `label_placeholders` catalog minus `CONTAINER_KEYS` — i.e. up to `asset_id`, `asset_name`, `serial_number`, `make`, `model`, `make_model`, `source_raw`, `source_ru`, `source_site`, `destination_raw`, `destination_ru`, `destination_site`, `move_name`, `move_date`, and `{}` when the catalog is empty. Reusing the resolver (rather than re-deriving the fields here) is what guarantees an offline kiosk renders the same values a generated label carries, RU formatting (`U14`) and all. 404 `initiative_not_found`; 422 `bad_initiative` when the initiative is not a move.
- `GET /kiosk/sync/people` → `KioskPeopleSyncOut {generated_at, people: [{id, display_name, rfid_tag, is_worker, has_account}]}`: every `Person` with `archived_at IS NULL` that has a `worker_profiles` row **or** a `user_accounts` row, ordered by last then first name. A plain contact (neither) is never included. This is a literal reading of "has a profile/account", not "is currently usable": a disabled `UserAccount` or an inactive `WorkerProfile` is still listed (`has_account`/`is_worker` don't check `disabled_at` or an active flag) — worth revisiting once the kiosk grows a timeclock that needs to tell "can badge in" from "is in the directory".

**Privacy note**: `/kiosk/sync/people` puts names and RFID tags into storage on the kiosk itself, where they survive a reload. That is internal directory data — no email, phone, or address is sent — and both endpoints are gated on `kiosk:view` like the rest of the router, with the same scope caveat (no initiative/client scoping; see the setup-options note above). The docstrings say so at the code.

**IndexedDB** (`src/lib/localDb.ts`, no library, hand-rolled like the portal's `lib/labelCache.ts`): database `serversherpa-kiosk` v1, stores `assets` (keyPath `id`; indexes `rfid`, `asset_id`, `serial_number`), `people` (keyPath `id`; index `rfid_tag`), `meta` (keyPath `key`). API: `openDb()`, `replaceAll(store, rows)` (clear + put in ONE transaction, so the store is never observably empty and a failed write aborts the clear with it), `replaceAllMulti(entries, meta?)` (the same clear-then-put per store, but for *several* stores plus an optional meta row in ONE transaction — used to write `assets`, `people`, and the `sync` meta pointer together so a reader never sees them half-updated; resolves with each store's post-write `count()`, read inside the same transaction so it reflects what actually landed rather than the length of the array the caller passed in), `count(store)`, `getAll(store)`, `getByIndex(store, index, value)`, `readMeta(key)`, `writeMeta(key, value)` (stores `{...value, key}`), `clearDb()`, plus `closeDb()` for tests. Unlike `labelCache.ts`, failures are **not** swallowed: a missing `indexedDB`, a blocked open, or a failed transaction rejects, so `sync.ts` can show a real error instead of a kiosk that believes it has data. `withStores` explicitly `tx.abort()`s when its callback throws (some IDB failures, like `put()` on a row missing its keyPath, throw synchronously without the transaction ever hearing about it) so a mid-write failure always rolls back every store in that transaction, not just the write that failed; its completion promise also gets a no-op `.catch` at creation so an aborted transaction never surfaces as an `unhandledrejection`. One long-lived connection is cached (reopening per scan costs a round trip); a failed open is never cached.

**Sync** (`src/lib/sync.ts`): `runSync(initiativeId, initiativeName)` fetches both endpoints in parallel (`fetchAssetsSync`/`fetchPeopleSync` in `lib/api.ts`, through `apiFetch`) and only then writes `assets`, `people`, and the `meta` row `{key: 'sync', initiativeId, initiativeName, assets: n, people: n, syncedAt}` together via `replaceAllMulti`. The counts it reports (both in `meta` and in the status below) come from `count('assets')`/`count('people')` against the store after the write, not the fetched payloads' lengths. Status is a store/hook in `setupState.ts`'s shape — `useSyncStatus()` → `{phase: 'idle'|'running'|'done'|'error', assets?, people?, syncedAt?, error?}` — with `readSyncStatus`/`subscribeSyncStatus`/`resetSyncStatus` and `formatSyncedAt(iso)` (time only). **Failure semantics**: a fetch error reports the `ApiError` code, a database error reports `'storage'`; because the writes happen only after *both* fetches resolve, the previously cached rows are untouched either way, and the status keeps the counts it already had so the footer doesn't blink. `phase` is effectively persisted through the meta row: `hydrateSyncStatus()` (run once from `useSyncStatus`'s first mount) turns an existing `sync` row into `done` + counts, so a reloaded kiosk shows its local data without re-fetching. **Re-entrancy**: a module-level run counter means a newer `runSync` call always supersedes an older one still in flight — the older run checks its own run number against the counter before every status update and before writing anything, and once it is no longer current it writes nothing and reports nothing, so tapping "Sync again" mid-sync can never let a slow first run clobber the second run's result.

**Trigger and UI**: `KioskSetup.tsx`'s successful save calls `runSync(result.initiative_id, result.initiative_name)` **without awaiting** — the summary card appears at once and the download reports itself. Sync outcomes never touch `kiosk_setup_complete`: the kiosk is set up whether or not the copy downloaded. The summary card gains a `.sync-status` block: `idle` (before a first sync, or after the Developer tab cleared the database — otherwise a dead end) → "No move data on this kiosk yet." with a "Sync now" `mini-btn`; `running` → "Downloading move data…"; `done` → "Local data: {assets} assets · {people} people · synced {time}" with a "Sync again" `mini-btn`; `error` → "Couldn't download move data ({code})." with "Try again". `KioskShell`'s footer appends a `Data` item ("{assets} assets · {people} people") once counts exist (never "0 assets" on a kiosk that has never synced). The Developer tab (dev mode on, like the setup-state selector) gains a read-only "Local data" row with the same counts and time — "Nothing downloaded yet." before a first sync — and a "Clear local data" `mini-btn` that calls `clearDb()` then `resetSyncStatus()` on success; a `clearDb()` rejection instead shows an inline `.form-error` ("Couldn't clear local data.") and leaves the sync status exactly as it was.

**Testing**: `api/tests/test_kiosk_sync_api.py` (roster fields incl. the populated `label` map, off-roster asset absent, non-move 422, unknown 404, people include a worker and an account holder with RFID and exclude an archived person and a plain contact, worker 200 / client_viewer 403). Kiosk: `lib/localDb.test.ts` and `lib/sync.test.ts` (both `// @vitest-environment jsdom` + `import 'fake-indexeddb/auto'`, a fresh `IDBFactory` per test; `fake-indexeddb` is a new kiosk devDependency, as in the portal), plus the sync cases in `KioskSetup.test.tsx`, `KioskShell.test.tsx`, and `Settings.test.tsx`.

**Deferred**: delta sync (the roster is replaced wholesale every time), periodic/background refresh (the kiosk syncs on setup and on demand only), and any size limit or eviction policy for the local database.

### Scan ingest (2026-09-14)

The kiosk scans offline against its local copy of the move and pushes matched scans up in batches.

**`POST /kiosk/scans`** (`routes/kiosk.py`, `kiosk:view`, **not** read-only exempt — it writes). Body `KioskScanBatchIn {serial: str, scans: [KioskScanIn]}` with **1-100 scans** (0 or 101 → 422), where `KioskScanIn = {client_scan_id: uuid, scanned_value: str (1-200, stripped), scan_type: "rfid" | "barcode", scanned_at: datetime, asset_id: uuid | None, site_id: uuid | None, initiative_id: uuid | None, scan_status: str | None}`. Response `KioskScanBatchOut {accepted: [uuid], rejected: [{client_scan_id, code}]}`.

- **The kiosk sends only scans it already matched locally**, and its match rides along as `asset_id` — informational only. The server re-matches `scanned_value` from scratch in the scan-matching worker, so a stale local database can never mis-attribute a scan.
- **One `raw_scans` row per scan** — the same inbox `scans/worker.py` drains — with `device_id` = the kiosk Device's **name** (the reader/kiosk identity string that table has always carried), `operator_id` = the signed-in person, `source = "kiosk"`, and `match_attempted_at` left NULL, which is exactly what `run_once()` selects on. There is no workflow status on a raw scan: "fresh" *is* `match_attempted_at IS NULL`; `status` is the asset-status checkpoint (migration 0026).
- **Defaults from the Device.** `site_id`, `initiative_id`, and `scan_status` fall back to the kiosk's own setup (`devices.site_id` / `current_initiative_id` / `scan_status`) whenever the scan omits them, so the normal payload carries only the tag and the time. The checkpoint is written to **both** `status` (the FK'd column the matcher copies into `processed_scans` and status rules trigger on) and the new `scan_status` (what the device reported, verbatim).
- **Idempotent on `client_scan_id`.** The kiosk generates that uuid; ingest is `INSERT … ON CONFLICT DO NOTHING` against a partial unique index, so a batch retried because the kiosk never saw the response stores nothing new and reports every scan accepted again — the kiosk can clear its outbox on any 200.
- **Per-scan rejection, never per-batch.** A scan naming a site, move, checkpoint, or scan type the server does not know is rejected on its own with `bad_site` / `bad_initiative` / `bad_status` / `bad_scan_type` and the rest of the batch still lands; the response is 200 with both lists. One stale row must not cost a truckload of scans. A checkpoint only has to *exist* — a status deactivated mid-move keeps ingesting. `bad_scan_type` covers a `scan_type` the Literal accepts (`rfid`/`barcode`) but the `scan` vocabulary no longer has a row for — renamed or deleted after the kiosk cached it. The whole batch fails only on an unknown or non-kiosk serial (404 `device_not_found`), a malformed body (422), or read-only mode (423).
- **Audit**: one row per batch — `entity_type="device"`, `entity_id` = the device id, `action="kiosk_scans"`, `changes={"accepted": n, "rejected": n}` (not one per scan; `raw_scans` is itself the log). The batch also stamps `device.last_seen_at`, but not `updated_at` — that still means "this kiosk's configuration changed".
- **Migration `0063_raw_scan_kiosk_fields.py`** (`down_revision="0062"`) adds three nullable columns to `raw_scans`: `client_scan_id` (uuid, UNIQUE where not null — the idempotency key), `scan_status` (text, deliberately **un**-FK'd device-reported data, the counterpart of `devices.scan_status`), and `initiative_id` (FK `initiatives.id ON DELETE SET NULL` — deleting a move must not delete scan history). Downgrade drops all three.
- **No serial ownership proof, same as setup and heartbeat.** `kiosk:view` is all this endpoint checks — it does not confirm the caller is the kiosk named in `serial`, so any `kiosk:view` holder can post scans attributed to any kiosk (its site, move, and checkpoint ride along, or fall back to that device's own setup either way). `operator_id` is never spoofable this way: it is always the signed-in actor, not anything the body supplies. Accepted alongside the heartbeat's and setup's no-ownership notes (see "Implementation notes") until device tokens.

**Deferred**: the kiosk-side outbox and retry loop, unmatched-scan feedback to the kiosk, `manual` scan type over this endpoint (the vocabulary has it; the kiosk has no keyed-entry screen yet), and any per-kiosk rate limit.

### Scanning (2026-09-14)

The kiosk's working screen (`pages/Scan.tsx`, route `/scan`, behind `KioskGuard` + `SetupGate` like the other features). It scans against the move downloaded to this kiosk and pushes matched scans to `POST /kiosk/scans` out of a durable outbox.

**The input.** One `.scan-input` at the top, always focused: a barcode scanner is a keyboard, so a value typed while focus sits elsewhere is silently lost. Focus is taken on mount, taken back after every submit, and reclaimed by a `focusout`/`visibilitychange` handler whenever it lands somewhere that is not an `input`/`button`/`select`/`textarea`/`a` on the page — so an operator typing into some other control on the page (Settings, say) is not fought for focus. The toolbar's own one-shot buttons (Retry failed, Clear sent, Discard failed) are the deliberate exception to that: they take focus to be clicked, but hand it straight back to the scan input once their action resolves, rather than sitting on it like a sustained focus target would. Enter submits; an empty or whitespace-only Enter is a no-op. The input is disabled — with "No move data on this kiosk. Sync it from Kiosk Setup." — while the local `assets` store is empty.

**Matching** (`lib/scanMatch.ts`). `buildScanIndex(assets)` builds three maps and `matchScan` tries them in this order: **RFID** (keys and input both zero-stripped with `displayRfid` and upper-cased, so a handheld's unpadded read matches a fixed reader's EPC), then **asset ID**, then **serial number** (both trimmed + upper-cased). First row wins a duplicate key. `scanTypeFor` reports `rfid` for a tag match and `barcode` for everything else — the vocabulary's `manual` is not used (the kiosk cannot yet tell a typed serial from a scanned one).

**Flash and sound** (`lib/flash.ts`, `components/ScanFlash.tsx`, `lib/appearance.ts`, `lib/sound.ts`). Every scan plays the Sound tab's sound for its outcome alongside the flash — `playScanSound('good' | 'not_found')` right beside `flash(...)`, and it swallows its own failures so a kiosk with no audio device still records the scan. A match flashes the whole screen `good_scan`; no match flashes `not_found_scan`. Both last `flash_ms` (the Appearance tab's Flash duration). Both colors live in `ss.kiosk.appearance` as HSL channels, kiosk-local (the right green for a dark cage is not the right green for an office, and the color belongs to the screen rather than the signed-in account), defaults `good {h:150,s:60,l:45}` / `not-found {h:0,s:70,l:50}`. The Appearance tab edits them with an `HslPicker` each — swatch, three sliders, `hsl(...)` readout, Preview flash (which fires for the configured duration) — persisting on every drag. The overlay is rendered once in `KioskShell` (fixed, `inset:0`, click-through, above the shell), fades 0.85 → 0 over its duration, and holds a short solid flash instead under `prefers-reduced-motion`.

**Outbox** (`lib/outbox.ts`, IndexedDB store `outbox` in **localDb v2**, keyPath `client_scan_id`, index `status`). Row: `{client_scan_id, seq, scanned_value, scan_type, scanned_at, asset|null, matched, status, attempts, next_attempt_at?, last_error?, site_id, initiative_id, scan_status}`; the matched asset is denormalized so the list keeps reading right after a re-sync, and `seq` (a persisted monotonic counter) orders the list because a reader can fire twice inside one millisecond.

| | |
|---|---|
| Batching | a scan schedules a flush **500 ms** out; a scan inside that window rides along rather than pushing it back, so nothing waits longer than one window. Up to **100** rows per POST. |
| Retry | a thrown `ApiError` (network, 5xx, 423) returns the whole batch with `attempts+1` and `next_attempt_at = now + BACKOFF[attempts]`, `BACKOFF = [2000, 4000, 15000, 60000]`; the attempt after the 60 s wait is terminal (`failed`). A timer wakes the sender at the earliest due row. |
| Per scan | the response's `accepted` ids go green; a `rejected` id is `failed` with its code immediately (`bad_site`/`bad_initiative`/`bad_status` will never succeed), as is an id the response mentioned in neither list (`no_ack`). |
| Restart | `startSender()` resumes `queued`/`retrying` rows on mount; a row left `sending` by a reload resets to `queued` — ingest is idempotent on `client_scan_id`, so re-sending one that landed is free. A storage failure mid-flush (the write that marks a batch `sending`) gets the same recovery without a reload: `flushOutbox`'s catch resets that batch back to `queued` and reschedules — otherwise `dueRows` would never pick it up again. |

**What is NOT sent:** unmatched scans. They are stored `nomatch` and never leave the kiosk (the endpoint only takes scans the kiosk matched); they exist so the operator sees that the tag they waved resolved to nothing. `outbox` is deliberately outside `STORES`, so Developer › "Clear local data" empties the cached roster without discarding scans that have not reached the API. No match rows expire 120 s after they were scanned; the sender sweeps every 10 s.

**The list** (`.scan-list`, `.local-table` shape, newest first): Serial, Name, RFID (`displayRfid`, raw EPC on `title`), Make / Model, a mono time, and a status chip — "Sent" (green), "Queued"/"Sending"/"Retrying (n/4)" (yellow), "Failed: {code}" and "No match" (red). A `nomatch` row shows the raw scanned value in the Serial cell and a dash elsewhere. Above it, `.scan-counts` reads "{queued} queued · {accepted} sent · {failed} failed" with **Retry failed** (failed rows back to `queued`, attempts 0), **Clear sent** (drops accepted/nomatch only — a scan the portal never received is not "sent" and stays out of this button's reach), and **Discard failed** (shown once something has failed; confirms "Discard N failed scans? They were never received by the portal." before dropping them).

**Storage failures are surfaced, not swallowed.** A rejected `enqueueScan` — a scan that never made it into IndexedDB at all — shows a persistent `.scan-storage-error` alert ("Couldn't save the scan to this kiosk's storage — the last value was not recorded.") that clears the next time a write succeeds; a rejected `retryFailed`/`clearSent`/`discardFailed` shows "Couldn't update the scan list." the same way. Neither is left to surface as an unhandled rejection — the promise is always given both a success and a failure handler.

**Deferred**: manual `scan_type` (no keyed-entry mode), camera scanning, per-scan overrides of the kiosk's site/move/checkpoint, and any unmatched-scan lookup against the server.

### RFID Enroll (2026-09-14)

Giving an asset its tag out on the floor (`pages/Enroll.tsx`, route `/enroll`, behind `KioskGuard` + `SetupGate`; the launcher tile sits immediately after Scanning). Jimmy: "we scan a serial or asset tag, and if a matching record is found we allow a second text input for the RFID tag... we save that tag value back to the asset in the portal. We also add a scan to the raw scans with a type of pre-stage."

**Two steps, one always-focused box at a time** — the Scanning page's focus rules, `focusout`/`visibilitychange` reclaim included, because both halves of the job are scans.

- **Step 1 — the asset.** `#enroll-asset-input` ("Scan a serial or asset ID"), matched by **asset ID or serial only** (`matchAssetOrSerial` in `lib/scanMatch.ts`, a narrowed sibling of `matchScan` — not `matchScan` itself, whose RFID-first order would let a tag that already belongs to something silently become "re-tag that"). A value that is an RFID tag in the local roster answers "That's an RFID tag. Scan the asset's serial or ID first."; anything else answers `No asset found for "{value}".` Both flash not-found and stay on step 1.
- **Step 2 — the tag.** A compact asset card (name, asset ID, serial, make/model, and the current tag via `displayRfid` when there is one, under the plain line "This asset already has a tag — scanning a new one replaces it."), then `#enroll-tag-input` ("Scan the RFID tag"), focused the moment the step renders, with a `mini-btn` **Cancel** back to step 1.

**The 24-character format, enforced twice.** `padRfid(raw)` (`lib/rfid.ts`) strips whitespace — inside as well as around, since a reader may space-separate an EPC — upper-cases, requires plain alphanumerics, caps at 24, and left-pads with zeros to exactly 24, which is how the house stores a tag (`displayRfid` strips the padding for display only). The padded value is shown under the box as it is typed ("Will be stored as `0000…100348`") so the operator sees what the portal will hold, and empty / over-length / non-alphanumeric values are refused there with their own copy before any call is made. The endpoint normalizes identically and independently (`normalize_rfid`): the preview is a courtesy, never the enforcement.

**`POST /kiosk/assets/{asset_id}/rfid`** (kiosk:view, NOT read-only exempt). Body `{serial, rfid_tag, scan_status, client_scan_id, site_id?, initiative_id?}`. In one transaction it loads the kiosk Device by serial (404 `device_not_found`) and the asset (404 `asset_not_found`), validates the checkpoint against the **active** asset vocabulary (422 `bad_status`), refuses a tag another asset already holds (409 `rfid_in_use`, whose detail carries that asset's `asset_id` and `asset_name`, so the screen can name it rather than showing a unique-index error), then sets `rfid_tag`, stamps `updated_at`, and audits `entity_type="asset"`, `action="kiosk_rfid_enroll"`, `changes={"rfid_tag": {"from", "to"}, "device": <kiosk name>}`. The same tag on the SAME asset is a success with `already_had_tag` and **no** audit row — nothing changed — but the scan is still written, because the operator really did wave a tag at a reader. Bad tags are 422 `bad_rfid` / `rfid_too_long`; a stale site or move is 422 `bad_site` / `bad_initiative` (checked rather than left to the scan's foreign keys). The scan is one `raw_scans` row shaped exactly as `POST /kiosk/scans` writes them — the padded tag as `scanned_value`, `scan_type='rfid'`, the checkpoint in both `status` and `scan_status`, `scanned_at` now, `device_id` = the Device name, `operator_id` = the signed-in person, site/move from the body or the Device, `source='kiosk'` — inserted `ON CONFLICT DO NOTHING` on `client_scan_id`, so a kiosk retrying a save it never saw the answer to records one scan. `device.last_seen_at` is stamped; `updated_at` is not (the kiosk's configuration did not change). Answer: `{asset_id, asset_name, asset_tag, serial_number, rfid_tag, already_had_tag}`.

**The checkpoint is configurable, on Settings › Admin.** A `.settings-row` "RFID Enroll checkpoint" with the hint "The scan type recorded when a tag is enrolled." and a native `<select>` of `getSetupOptions()`'s `scan_types`, stored kiosk-local in `lib/enrollSettings.ts` (`ss.kiosk.enrollStatus`, the `devMode.ts` store/hook shape), defaulting to **`pre_stage`** when unset or when the stored key is no longer offered (`effectiveEnrollStatus`). This is the Admin tab's first real content, and it is admin-gated on purpose: it decides what checkpoint every enrollment on this kiosk records — that is move data, and a worker should not be able to change it silently. Non-admins never see the row; the default still applies to them. A failed options fetch is a note ("Couldn't load the checkpoint list. The stored choice still applies."), not a blocked screen.

**Saving.** The call carries the kiosk serial, the setup's site and move, the configured checkpoint and a fresh `client_scan_id`. On success: the good flash for `flash_ms`, the good sound, the asset's `rfid` updated in the local IndexedDB roster (so Scanning recognizes the tag immediately, without waiting for a sync), a toast "Enrolled {asset} → {trimmed tag}", and back to step 1 focused and empty. On failure: the not-found flash and sound, the tag box cleared and refocused on step 2, and mapped copy — `rfid_in_use` "That tag is already on {name}.", `bad_rfid` / `rfid_too_long` the local copy, 423 "The portal is in read-only mode. Try again shortly.", `network` "Can't reach the portal. The tag was not saved.", anything else "Couldn't save the tag ({code})."

**Online only, deliberately.** There is no outbox here — the contrast with Scanning is the point: that screen queues because a dock loses signal mid-shift and a scan is an observation that can land late, whereas whether a tag is already on another asset is a question only the portal can answer. A save that did not reach the portal did not happen, and the screen says so rather than promising to send it later.

**A session-only list of this session's enrollments (2026-09-14).** Below the input, once at least one tag has been saved, a `.local-table`-shaped list (`.enroll-list`, in a `.local-table-wrap.enroll-list-wrap` capped at the wide fluid width `clamp(20rem, 82vw, 90rem)` so a narrow screen scrolls the table rather than the page) shows **Name**, **Serial** (em dash when absent), and **RFID** (`displayRfid`, the full 24-character padded value on the cell's `title`), newest first, capped at the last **25**. A fourth, unlabeled column carries the local time in mono, the same idiom as the Scanning list. An enrollment that replaced a *different* existing tag — `target.rfid` was set before the save and the response's `already_had_tag` came back false — gets a small `.chip.tag` reading "replaced" in the RFID cell; the same-tag rescan case (`already_had_tag: true`, nothing actually changed) does not. It lives in React component state only, never IndexedDB, so a reload clears it — the same call the Timeclock screen made for its own recent list (and then removed, 2026-09-14) for the same reason: the portal's asset record and the enrollment scan are the record of truth, and a kiosk-local cache of "what I did" is a convenience for the operator standing there right now, not a second copy of history worth persisting or syncing.

**Deferred**: bulk enroll (one asset after another without returning to step 1), reviewing re-tagging history on the kiosk (the audit rows exist; reading them is a portal job), and container tags (`containers.rfid_tag` has the same shape; the Containers screen below now reads them, but enrolling one is still a portal job).

### Containers (2026-09-14)

Packing and unpacking crates out on the floor (`pages/Containers.tsx`, route `/containers`, behind `KioskGuard` + `SetupGate`; the launcher tile sits immediately after RFID Enroll, with a crate-shaped 40px icon — the launcher already wraps at five tiles per row, so nothing else moved). Jimmy: "Scan a container, then scan assets to add or remove them. Each scan writes a raw scan and updates the asset's container membership."

**Container sync and store.** The kiosk had no containers at all before this, so the sync run gained a third endpoint. `GET /kiosk/sync/containers?initiative_id=<uuid>` (`kiosk:view`, one response, no paging — a move's crate list is tens to a few hundred rows) returns `KioskContainersSyncOut {initiative_id, generated_at, containers: [{id, name, rfid_tag, label_tag, container_type, status, status_label, site_id, site_name, asset_count}]}`: every container whose `initiative_id` is this move (migration 0057's link) and whose `archived_at` is NULL, ordered by name, with `asset_count` from a grouped count over `container_assets`. Archived crates are left out — a kiosk must not be able to pack into something the portal retired. 404 `initiative_not_found`, 422 `bad_initiative` for a non-move: the same contract as `/sync/assets`.

`runSync` now fetches all three endpoints in parallel and writes `assets`, `people`, `containers`, and the `meta` row together in the one `replaceAllMulti` transaction, so a reader never sees them half-updated; the meta row and `useSyncStatus()` gained a `containers` count (a kiosk whose last sync predates this reads it as 0), and the three places that print the counts — the shell footer, Kiosk Setup's summary card, and Settings › Developer's "Local data" row — append "· {n} containers".

**IndexedDB is v4**: a `containers` store (keyPath `id`, indexes `rfid_tag` and `name`) alongside the five v1-v3 stores. `onupgradeneeded` still only creates what is missing, so a kiosk at v1, v2, or v3 keeps its downloaded move and its queued scans and simply gains the store; the `versionchange` yield added in v2 is untouched. `containers` **is** in `STORES`, so Developer › "Clear local data" empties it with `assets`, `people`, and `meta` — it is cached move data, re-downloadable from Kiosk Setup, and a stale crate list outliving its move would be worse than an empty one. `outbox` and `sounds` stay outside `STORES` exactly as before, so nothing about this touches scans that have not reached the API or files someone uploaded.

**Step 1 — the container.** `#container-input` ("Scan a container tag or type its name", `aria-label="Container tag or name"`), always focused under the Scanning page's focus rules. `lib/containerMatch.ts` indexes the synced crates three ways and `matchContainer` tries them in the order a scan is most likely to be: **RFID** (keys and input both zero-stripped with `displayRfid` and upper-cased, the `scanMatch.ts` rule, so a handheld's unpadded read matches a fixed reader's EPC), then **label tag** (the five Container Labels keys — deliberately a weak identifier: `label_tag` is NOT unique, so first row wins and a name or a tag should be preferred where there is one), then **name**, case-insensitively and **exactly**. A partial name is never a match: several crates on a move differ only by their trailing number (`SC-DAL_PAL-001`, `-002`, …), so `searchContainers` offers up to eight of them as a short tappable list (`.tc-results`/`.tc-result`, the Timeclock idiom) and the operator picks. Nothing at all matches → the not-found flash and sound plus `No container found for "{value}".`

**Step 2 — the assets.** A `.ct-card` header — the crate's name, type, status label, site, and a **live asset count** that moves with every pack and unpack — over a `.segmented` **Pack / Unpack** toggle (`role="radiogroup"`, Pack by default) and `#container-asset-input` (`aria-label="Asset tag, ID, or serial"`). Switching the toggle clears the box and refocuses it: a value scanned for "pack" must never be sent as an unpack because the toggle moved under it. The asset box uses `matchScan`'s **full** order — RFID, asset ID, then serial. Unlike RFID Enroll's first step, an RFID read here is a perfectly good way to say which asset you are holding: nothing is being written onto the tag, so there is no risk of silently re-tagging whatever it already belongs to. An asset the kiosk does not know never reaches the portal (`No asset found for "{value}".`). A `mini-btn` **Done** returns to step 1 with everything cleared.

**`POST /kiosk/containers/{container_id}/assets`** (`kiosk:view`, NOT read-only exempt — it writes). Body `KioskContainerAssetIn {serial, asset_id, action: "pack" | "unpack", scanned_value, scan_type: "rfid" | "barcode", scan_status, client_scan_id, site_id?, initiative_id?}`. In **one transaction** it loads the kiosk Device by serial (404 `device_not_found`), the container (404 `container_not_found`, archived included — a retired crate is gone as far as the kiosk is concerned), and the asset (404 `asset_not_found`), validates the checkpoint against the **active** asset vocabulary (422 `bad_status`), and checks a stale site or move itself (422 `bad_site` / `bad_initiative`) rather than leaving it to the scan's foreign keys. Then:

- **`pack`.** `container_assets.asset_id` is **UNIQUE** — an asset is in at most one container — so the outcome follows from where the asset already is. Already in **this** container: a no-op, `already_there: true`, **no** second audit row, but the scan is still written because the operator really did wave something at a reader. In **another** container: the old membership row is deleted and flushed before the new one is inserted (so the unique index never sees both), and the answer's `moved_from` names the crate it came out of. In no container: a plain insert. Audit `entity_type="container"`, `entity_id` = this container, `action="kiosk_container_pack"`, `changes={"asset_id", "asset_name", "from_container": <name|null>, "device": <kiosk name>}`.
- **`unpack`.** An asset that is not in this container is **409 `not_in_container`**, whose detail carries the `container_id` / `container_name` it actually *is* in when it is in one, so the screen can name the right crate rather than silently emptying the wrong one; an asset in no container gets the same code with nothing named. Otherwise the row is deleted and audited `kiosk_container_unpack` with the same `changes` shape (`from_container` = this container).

Either way exactly **one `raw_scans` row** is written, shaped as `POST /kiosk/scans` writes them — `scanned_value` and `scan_type` as the kiosk read them (not the asset id: the matcher must be able to resolve the scan independently), the checkpoint in both `status` and `scan_status`, `scanned_at` now, `device_id` = the Device name, `operator_id` = the signed-in person, site/move from the body or the Device, `source='kiosk'` — inserted `ON CONFLICT DO NOTHING` on `client_scan_id`, so a kiosk retrying a call it never saw the answer to records one scan. `device.last_seen_at` is stamped; `updated_at` is not. Answer: `{container: {id, name, asset_count}, asset: {id, name, asset_tag, serial_number, rfid}, action, moved_from: {id, name} | null, already_there}` — the count comes back from the database inside the transaction, so the card never has to guess.

**Two more configurable checkpoints, on Settings › Admin.** "Container pack checkpoint" (default **`in_container`**) and "Container unpack checkpoint" (default **`un_pack`**) sit beside the existing "RFID Enroll checkpoint" (`pre_stage`), each a native `<select>` of `getSetupOptions()`'s `scan_types`. All three are admin-gated for the same reason: each decides what checkpoint every scan of its kind on this kiosk records — that is move data, and a worker should not be able to change it silently. The three near-identical modules were collapsed into one, `lib/checkpointSettings.ts` (`readCheckpoint`/`writeCheckpoint`/`effectiveCheckpoint`/`useCheckpoint`/`defaultCheckpoint`, keyed by `'enroll' | 'containerPack' | 'containerUnpack'`), replacing `lib/enrollSettings.ts`; the enroll row keeps its original storage key `ss.kiosk.enrollStatus` so a kiosk already configured does not silently revert, and the two new ones are `ss.kiosk.containerPackStatus` / `ss.kiosk.containerUnpackStatus`. A stored key the portal no longer offers falls back to **that checkpoint's own** default. The Admin tab now renders one shared `CheckpointRow` per entry and shows the "Couldn't load the checkpoint list. The stored choice still applies." note once for the tab, not once per row — all three read the same vocabulary, so they fail together.

**Online only, deliberately** — the same call RFID Enroll made, and the deliberate contrast with Scanning's outbox two sections up. Scanning queues because a dock loses signal mid-shift and a scan is an observation that can land late; container membership is **relational state the kiosk cannot resolve alone**: only the portal knows which other crate holds an asset, and therefore whether a pack is an insert or a move. A scan that did not reach the portal did not happen, and the screen says so rather than promising to send it later. An **offline queue is the obvious follow-up** and is deferred below.

**The session list.** Below the input, once at least one scan has landed, a `.local-table`-shaped list (`.ct-list` inside a `.local-table-wrap.ct-list-wrap` at the wide fluid width `clamp(20rem, 82vw, 90rem)`) shows **Asset**, **Serial**, **RFID** (`displayRfid`, the padded value on the cell's `title`), a `.chip.tag` reading **Pack** or **Unpack**, and the local time in mono — newest first, capped at the last **50**. A `moved_from` answer adds a small `.ct-moved` note under the asset's name ("moved from {name}") so nobody wonders why another crate just got lighter. React state only, never IndexedDB: a reload clears it — and so does **Done**, because the list is this crate's context rather than a log, and leaving the last crate's rows under the next crate's card would read as "these are in here". The portal's container record and the pack/unpack scans are the record of truth (the same call Timeclock and RFID Enroll made).

**Error copy**: `not_in_container` "That asset is in {name}, not this container.", a local miss `No asset found for "{value}".`, `container_not_found` "That container is gone — scan it again.", `read_only_mode`/423 "The portal is in read-only mode. Try again shortly.", `network` "Can't reach the portal. That scan was not recorded.", anything else "Couldn't record that ({code})."

**Testing**: `api/tests/test_kiosk_containers_api.py` (sync returns the move's crates with counts and excludes archived ones and other moves'; pack writes membership + one audit row + one scan; a pack of an asset held elsewhere moves it and reports `moved_from`; packing twice into the same crate is a no-op with one audit row and two scans; unpack removes it; unpacking something that is elsewhere is 409 naming that crate; unknown ids 404; bad or inactive checkpoint 422; a replayed `client_scan_id` adds no second scan; worker 200 / `_client_viewer` 403 / read-only 423; and the scan-matching worker draining the pack's scan end to end). Kiosk: `lib/containerMatch.test.ts`, `lib/checkpointSettings.test.ts`, the v4 and Clear-local-data cases in `lib/localDb.test.ts`, the third store in `lib/sync.test.ts`, `pages/Containers.test.tsx`, and the two new Admin rows in `pages/Settings.test.tsx`.

**Deferred**: creating a container at the kiosk (naming, type, site — a portal job today), printing a container label from this screen (`/labels` owns the printer, and `containers.label_tag` is already synced for it), and the **offline queue** — the honest follow-up to "online only", which needs the server to resolve a queued pack against wherever the asset has since moved.

### Trucks (2026-09-14)

Loading and unloading trailers out on the dock (`pages/Trucks.tsx`, route `/trucks`, behind `KioskGuard` + `SetupGate`; the launcher tile sits immediately after Containers, with a tractor-and-trailer 40px icon — the launcher caps at five tiles per row, so the eighth tile simply wraps onto a second row and nothing else moved). Jimmy: "Scan a truck, then scan containers or assets onto or off it. Writes scans and updates what each item is loaded on, so the portal's truck detail reflects the floor." This screen is Containers' sibling and is built to feel identical: pick the thing once, then scan repeatedly against it.

**Truck sync and store.** `GET /kiosk/sync/trucks?initiative_id=<uuid>` (`kiosk:view`, one response, no paging — a move has a handful of trucks) returns `KioskTrucksSyncOut {initiative_id, generated_at, trucks[]}`, each truck carrying `{id, name, load_number, status, status_label, driver_name, start_site_id, start_site_name, end_site_id, end_site_name, container_count}` — the move's unarchived trucks, ordered by name, with the ride-along counts read in one grouped query. Unknown move is 404 `initiative_not_found`, a non-move 422 `bad_initiative`, exactly as `/sync/containers` answers. Archived trucks are left out: a kiosk must not be able to load something the portal retired. `runSync` now fetches **four** endpoints in parallel and writes `assets`, `people`, `containers`, `trucks`, and the `meta` row in the one `replaceAllMulti` transaction; the meta row and `useSyncStatus()` gained a `trucks` count (a kiosk whose last sync predates this screen reads 0 until it syncs again), and the "Local data" lines on Kiosk Setup and Settings › Developer say so.

**IndexedDB is v5**: a `trucks` store (keyPath `id`, indexes `name` and `load_number` — the two things a truck is identified by; it has no RFID tag) alongside the six v1-v4 stores. `onupgradeneeded` still only creates what is missing, so a kiosk at v1, v2, v3, or v4 keeps its downloaded move and its queued scans and simply gains the store; the `versionchange` yield-the-connection handler is untouched. `trucks` joins `STORES`, so **Clear local data** empties it with the rest of the cached move and still leaves the outbox and uploaded sounds alone — the same treatment `containers` gets, for the same reason: a stale truck list that outlived its move would be the one thing still recognizing it.

**Step 1 is a card picker, not a scan box** — the one real difference from Containers, and it follows from the data rather than from taste. A crate carries an RFID tag and a printed Container Labels key; **a truck carries neither** (`trucks` has no `rfid_tag` column, and there is nothing on a trailer to read), and a move has a handful of them rather than hundreds. So the step looks like the Kiosk Setup wizard: one `.setup-card` per synced truck showing what tells trailers apart out on the yard — name, load number, status chip, driver, the route as "{start} → {end}", and how much is already aboard. Above the cards a `.dir-search` filter (focused on mount, `aria-label="Filter trucks"`) narrows by name **or** load number so a long list stays fast; typing a full name or load number and pressing Enter selects that truck outright. That last case is all `lib/truckMatch.ts` does beyond filtering, and the match is **exact** for the same reason `matchContainer`'s is — `TRUCK-1` is a prefix of `TRUCK-10`, and guessing between them would put a crate on the wrong trailer. Name beats load number when a string is somehow both: the name is what is painted on the door. No trucks at all reads "No trucks on this move. Ask a coordinator to add one."

**Step 2 takes a container OR an asset.** A `.ct-card` header — the truck's name, load number, status, route, and a **live container count** that moves with every load and unload — over a `.segmented` **Load / Unload** toggle (`role="radiogroup"`, Load by default, clearing and refocusing the box on change so a value scanned for one action is never sent as the other) and `#truck-container-input` (`aria-label="Container tag or asset"`, "Scan a container, or an asset inside one") under the Scanning page's focus rules. **Trucks carry containers** — `truck_containers` is keyed on `(truck_id, container_id)` and there is no asset-to-truck link at all — but the thing in someone's hand on a dock is often an asset, so the box resolves both, in order: a **container** first (`containerMatch.ts`: RFID, label tag, exact name), then an **asset** (`scanMatch.ts`: RFID, asset ID, serial) whose crate is what actually gets loaded, with "via asset {name}" on that row so nobody thinks the asset moved by itself. The asset → crate hop is local: `/kiosk/sync/assets` now carries `container_id` per asset (at most one, by the UNIQUE constraint on `container_assets.asset_id`) precisely so a scan costs no round trip. An asset in **no** container cannot be loaded and says exactly that — "That asset isn't in a container yet — pack it first." — without calling the portal; nothing matched at all names the value.

**`POST /kiosk/trucks/{truck_id}/containers`** (`kiosk:view`, NOT read-only exempt — it writes). Body `KioskTruckContainerIn {serial, container_id, action: "load" | "unload", scanned_value, scan_type, scan_status, client_scan_id, site_id?, initiative_id?}`. In **one transaction** it resolves the kiosk Device by serial (404 `device_not_found`), the truck (404 `truck_not_found`, archived included) and the container (404 `container_not_found`, archived included), validates the checkpoint against the **active** asset vocabulary (422 `bad_status`) and `scan_type` against the scan vocabulary — `status_values` `record_type='scan'`, which is what `raw_scans.scan_type` is foreign-keyed to (422 `bad_scan_type`) — and checks a stale site or move up front (422 `bad_site` / `bad_initiative`) rather than leaving it to the scan's foreign keys. Then:

- **`load`.** A crate rides one truck at a time, so the outcome follows from where it already is. Already on **this** truck: a no-op, `already_there: true`, **no** second audit row, but the scan is still written because the operator really did wave something at a reader. On **another** truck: a **MOVE** — the old link is deleted and flushed before the new one is inserted, and `moved_from` names the trailer it came off so the screen can print "moved from {truck}" rather than leaving someone to wonder why another load got lighter. Otherwise a plain insert. Audit `entity_type="truck"`, `entity_id=<truck>`, `action="kiosk_truck_load"`, `changes={container_id, container_name, asset_count, from_truck, device}`.
- **`unload`.** A container that is not on this truck is **409 `not_on_truck`**, whose detail carries the `truck_id` / `truck_name` it actually *is* on when it is on one, so the screen can name the right trailer rather than silently emptying the wrong one; a container on no truck gets the same 409 with nothing named. Otherwise the link is deleted and audited as `kiosk_truck_unload` with the same `changes` shape.

Either way exactly **one `raw_scans` row** is written, shaped as `POST /kiosk/scans` writes them — `scanned_value` and `scan_type` as the kiosk read them (which may be the **asset** someone scanned, not the crate that moved: the matcher must be able to resolve the scan independently), the checkpoint in both `status` and `scan_status`, `scanned_at` now, `device_id` = the kiosk Device's name, `operator_id` = the signed-in person, site / move from the body falling back to the Device's own setup, `source='kiosk'`, `match_attempted_at` NULL so the scan-matching worker drains it — and idempotent on `client_scan_id` via the same `ON CONFLICT DO NOTHING` against the partial unique index, so a kiosk retrying a call it never saw the answer to records one scan, not two. `device.last_seen_at` is stamped; nothing else about the kiosk's configuration moves. The answer is `{truck: {id, name, container_count}, container: {id, name, asset_count}, action, moved_from, already_there}`, with both counts read fresh inside the transaction.

**Two more configurable checkpoints, on Settings › Admin.** "Truck load checkpoint" (default **`on_truck`**) and "Truck unload checkpoint" (default **`received`**) join the three that were already there, through the same `lib/checkpointSettings.ts` module and the same `CHECKPOINT_ROWS` table — five rows differing only in storage key, default, and label, so still one component rather than five near-copies. The defaults are real keys in the house asset vocabulary, confirmed in the dev database: `on_truck` is its own word for a crate riding a trailer, and `received` is chosen over `un_pack` because coming off a truck is an **arrival** — opening the crate is a separate scan that belongs to the Containers screen. Admin-gated for the same reason the others are: each decides what every scan of its kind on this kiosk records, and a worker should not be able to change what the move's data says.

**Online only, deliberately** — the same call Containers made, and the same deliberate contrast with Scanning's outbox. Which truck carries a crate is **relational state the kiosk cannot resolve alone**: only the portal knows whether that crate is already on another trailer, and a queued "load" replayed an hour later could move a crate off a truck that has since departed. So there is no outbox here; a call that did not reach the portal did not happen, and the screen says "Can't reach the portal. That scan was not recorded." rather than promising to send it later.

**The session list.** Below the input, once at least one scan has landed, a `.local-table`-shaped list (`.ct-list` inside `.local-table-wrap.ct-list-wrap`, the same wide fluid width Containers uses) shows **Container**, **Assets** (the crate's own asset count), a Load / Unload chip, and the time, with the "moved from {truck}" and "via asset {name}" notes under the container name. Newest first, capped at fifty rows, React state only — it is this trailer's context, not a log, so **Done** clears it along with everything else and returns to the picker (leaving the last truck's rows under the next truck's card would read as "these are on it", which is exactly wrong). The portal's truck record and the load / unload scans are the record of truth.

**Error copy**: `not_on_truck` → "That container is on {name}, not this truck." (or "That container isn't on a truck." when nothing is named), `container_not_found` → "That container is gone — scan it again.", `truck_not_found` → "That truck is gone — pick it again.", `read_only_mode` / 423 → "The portal is in read-only mode. Try again shortly.", a network failure → "Can't reach the portal. That scan was not recorded.", anything else → "Couldn't record that ({code})." — the portal's own code kept in the fallback so a surprise is still reportable.

**Deferred**: changing a truck's status from the kiosk (depart / arrive is a coordinator's call today, and `status_values` `record_type='truck'` already has the keys for it); checking a load off against a manifest (what *should* be on this trailer, versus what has been scanned onto it); seal capture and verification (`trucks.seal_id` exists and nothing on this screen touches it); loading a loose asset by creating or choosing a crate for it on the spot; and an offline queue (see above — it needs a conflict story first, and would be the same design Containers needs).

### Pairing

Table `kiosk_pair_requests`:

| column | type | notes |
|---|---|---|
| id | uuid pk | |
| code | text unique | 8 chars, Crockford base32 alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`, `secrets.choice` |
| poll_token_hash | text | sha256 of the 32-byte urlsafe token returned once to the kiosk |
| serial | citext | kiosk serial |
| kiosk_name | text | |
| status | text | `pending` / `approved` / `denied` / `claimed`; expiry is derived from `expires_at`, never stored |
| approved_by | uuid null fk people | |
| ip_address | text null | creator IP |
| expires_at | timestamptz | created + 300 s |
| created_at | timestamptz | |
| updated_at | timestamptz | |

Index on `(ip_address, created_at)` for the rate limit and on `(serial)` for lookups (codes for the same serial are independent — see Implementation notes).

Endpoints:

- `POST /kiosk/pair` — **unauthenticated**. Body `PairCreateIn {serial: str (1–120), name: str (1–80)}`. Rules, in order: delete rows older than 24 h (cheap opportunistic cleanup); if `count(*) where ip_address = :ip and created_at > now() - 5 min >= 30` → 429 `pair_rate_limited`; insert; return `PairCreateOut {code, poll_token, link_url, expires_at}` where `link_url = f"{settings.portal_origin.rstrip('/')}/link/{code}"`. Read-only exempt (see below).
- `POST /kiosk/pair/{code}/poll` — **unauthenticated**. Body `{poll_token}`. 404 `pair_not_found` if no row; 403 `pair_forbidden` if the token hash mismatches (constant-time compare). Then: past `expires_at` → `{status: "expired"}`; `pending`/`denied`/`claimed` → `{status}` (`claimed` reported as `expired`, a one-shot code is spent); `approved` → mint a session for `approved_by` via `start_session(audit_action="login_pair")` with the kiosk's IP and user agent, set the refresh cookie, set status `claimed`, return `PairPollOut {status: "approved", session: SessionOut}`. If `approved_by`'s account is now disabled or has no `kiosk:view` → status `denied`. Read-only exempt.
- `GET /kiosk/pair/{code}` — requires `kiosk:view`. Returns `PairInfoOut {code, kiosk_name, serial, status, expires_at}` with `status` computed (`expired` when past). 404 when unknown.
- `POST /kiosk/pair/{code}/approve` — requires `kiosk:view`. 404 unknown; 409 `pair_not_pending` unless `pending` and unexpired. Sets `approved`, `approved_by = actor.person.id`, audits `kiosk_pair_approved` (entity `kiosk_pair`, changes `{serial, kiosk_name}`). 204. Read-only exempt (it is a sign-in).
- `POST /kiosk/pair/{code}/deny` — same gate; 409 unless pending; sets `denied`; audits `kiosk_pair_denied`; 204. Read-only exempt.

`deps.READ_ONLY_EXEMPT_PREFIXES` gains `"/kiosk/pair"`; `/kiosk/heartbeat` is **not** exempt (it writes a Device row and the kiosk tolerates failure).

Security notes, recorded so the review does not re-derive them: 40-bit codes with a 5-minute life and a per-IP creation cap; the code alone cannot claim a session because the poll token is required; approve is an authenticated action gated on the approver's own kiosk permission; the phone page names the kiosk and its serial so a user is not tricked into signing in a stranger's kiosk without seeing it; the session minted at claim time is a fresh family for the kiosk, so revoking it never touches the approver's phone session.

### Heartbeat

`POST /kiosk/heartbeat` — requires `kiosk:view`. Body `HeartbeatIn {serial: str, name: str, mode: Literal["web","laptop","pi","android","ios"], version: str | None, raw_info: dict = {}, sign_in: bool = False, login_method: Literal["password","link"] | None = None}`.

- Look up `Device` by `serial` (the existing partial unique index `devices_serial_uniq` covers this). None → insert `Device(device_type="kiosk", name, serial, sub_type=mode, version, raw_info, last_seen_at=now)`. Found with `device_type != "kiosk"` → 409 `serial_conflict`. Found kiosk → update `name`, `sub_type`, `version`, `raw_info` (merged, kiosk keys win), `last_seen_at`, `updated_at`.
- Returns `HeartbeatOut {device_id, name, registration: "ok"|"soon"|"expired"|"none", token_expires_at}` using the Kiosk Devices thresholds (7 days).
- Not audited (a heartbeat is telemetry); creation is audited once (`action="self_register"`, actor = signed-in person).
- **Sign-in auto-registers the kiosk and records who's on it.** `sign_in` is true only on the one heartbeat the kiosk sends right after a person signs in (password login or a completed pairing) — never on a cookie restore, never on a periodic tick. That beat carries `login_method` ("password" or "link") and the handler stamps `device.session_person_id = actor.person.id`, `device.session_login_method = login_method`, `device.session_started_at = now` — this is what the Kiosk Devices "Signed in"/"Login" columns read. Independently, when the kiosk's registration is not `"ok"` (i.e. `"none"`, `"expired"`, or `"soon"` — within 7 days of expiring), the same beat stamps `registered_at = now` and `token_expires_at = now + 30 days` (`KIOSK_AUTO_REGISTER_DAYS`, matching the portal's Register default) and writes an audit row exactly like the portal's Register action (`action="register"`, `entity_type="device"`) but `changes` carries an extra `source: "kiosk_sign_in"` key and the actor is the signed-in kiosk user. A sign-in on a kiosk that is already `"ok"` (more than 7 days left) changes nothing about the registration and audits nothing, but still records the new session.
- **`POST /kiosk/sign-out`** — requires `kiosk:view`. Body `{serial: str}`. Finds the kiosk `Device` by serial; if found and `session_person_id` is null or equal to the caller's person, clears `session_person_id`/`session_login_method`/`session_started_at` and stamps `updated_at`. Always 204 — an unknown serial or someone else's session is not an error, since the kiosk is about to drop its own token either way. Not read-only exempt (it writes; the kiosk ignores failures — see `signOutRequest`).
- **`DeviceItem` session fields**: `session_person_id`, `session_person_name` (built the same way as `Person.display_name`, via an outer join so a kiosk with no session reads null), `session_login_method`, `session_started_at`.
- **Kiosk Devices columns**: "Signed in" (the session person's name, or "—") and "Login" (a chip: "Password" / "Phone link" / "—"), both default-on, placed after Registration. A kiosk that vanishes without signing out (crash, unplugged, closed tab) keeps showing its last signed-in user until the next sign-in — there's no server-side timeout on the session fields. Stale detection is deferred; `last_seen_at` (already on the row) is the tell that the "Signed in" name may be stale.

### Timeclock (2026-09-14)

The kiosk punch clock: a worker walks up, is found by badge, RFID, or typed name against the synced people list, and is clocked in or out. The rows are ordinary `time_entries` — the portal's own time tracking — so a kiosk punch shows up in `GET /time/entries`, `/time/active`, the per-initiative summary and the approval queue like any other. All three endpoints require `kiosk:view`; the two POSTs write, so neither is read-only exempt.

- **`GET /kiosk/timeclock/{person_id}`** → `KioskTimeclockStatusOut {person: {id, display_name, first_name, last_name, preferred_name, avatar_url, rfid_tag}, clocked_in: bool, entry: {id, started_at, initiative_id, initiative_name, site_id, site_name} | null, last_entry: {...} | null}`. `entry` is the person's open entry (`clock_out_at IS NULL`) — the kiosk shows the avatar and counts up from `started_at`. `avatar_url` is presigned and short-lived (the same `presign_get(person.avatar_key)` the portal uses), null without an avatar. When there is no open entry, `last_entry` is the person's most recently CLOSED entry (`clock_out_at IS NOT NULL`, latest `clock_out_at` first) as `{id, started_at, ended_at, minutes}` — null when they have never clocked out; while clocked in, `last_entry` is left null (the open entry is what the card shows instead). 404 `person_not_found` for an unknown **or archived** person (the people sync drops archived people too, so only a stale local cache asks).
- **`POST /kiosk/timeclock/clock-in`** — body `{serial, person_id, site_id?, initiative_id?}`. Opens an entry with `clock_in_at = now` — deliberately no `at`; see the security note below. `site_id` / `initiative_id` fall back to the kiosk Device's `site_id` / `current_initiative_id`, so the punch inherits the move and site from Kiosk Setup. Provenance: `source = "kiosk"` and `device_id` = the kiosk's Device (migration 0064). Audited `entity_type="time_entry"`, `action="kiosk_clock_in"`, `actor_id` = the signed-in operator, `changes = {person_id, site_id, initiative_id, device_id}`. Errors: 404 `device_not_found` / `person_not_found`; 409 `already_clocked_in` with the open entry's id in `detail.entry_id` (so the kiosk can offer "clock out" instead); 422 `bad_site` / `bad_initiative` when an id doesn't exist — 422 rather than 404 because a kiosk holding a stale setup is the likely cause. Returns the status shape, now clocked in.
- **`POST /kiosk/timeclock/clock-out`** — body `{serial, person_id}`. Closes the open entry with `clock_out_at = now` — also no `at`, so there is nothing to validate against `clock_in_at` and no `bad_time` error — and graduates it to `pending`, exactly as self-service clock-out does, so it lands in the timesheet-approval queue. 409 `not_clocked_in` when there is no open entry. Audited `kiosk_clock_out` with the close diff plus `person_id` and `device_id`. Returns the status shape with `clocked_in: false`, `entry: null`, and `last_entry {id, started_at, ended_at, minutes}` so the kiosk can say "Clocked out after 3h 12m" without a second call.
- **No `at` on either punch, deliberately (2026-09-14 review).** `kiosk:view` includes the worker role, which deliberately has no `time` grants; an unbounded `at` would let a worker post a back-dated clock-in and land a fabricated multi-hour row in the approval queue with `adjusted = false` and no `adjust_reason`, routing around the portal's own edit controls (`routes/time.py` requires `time:change` + `adjust_reason` and stamps `adjusted`). The kiosk has no offline queue (below) and so never had a caller for `at`. Back-dating a punch stays a portal action.
- **`GET /kiosk/sync/people`** additionally carries `first_name`, `last_name` and `preferred_name` per person, so the kiosk can match a typed name in any order without re-splitting `display_name`.
- **Any kiosk user can punch any worker.** Unlike `/time/clock-in`, which acts strictly on the caller's own person id, these act on ANOTHER person and check nothing but `kiosk:view` — deliberate, and the same accepted risk as the rest of this router (no serial ownership proof either). It matches the physical situation: one shared screen on a dock, one person tapping it for whoever is in front of them. Every punch is attributable — the audit row's actor is the signed-in operator, never the punched worker, and `device_id` names the kiosk.
- **Shared entry mechanics.** `services/timeclock.py` owns the rules both paths must agree on: one open entry per person (the advisory pre-check plus the `one_open_entry_per_person` partial unique index, surfaced as a clean 409 from a savepointed flush — `create_open_entry` inspects the raw driver exception's constraint name so a *different* IntegrityError, such as a bogus `device_id`, is never misreported as `already_clocked_in`), closing into `pending`, and worked minutes as span-minus-break, never negative. `routes/time.py` was moved onto it with no behavior change (its clock-out handler now calls `timeclock.open_entry_for` instead of inlining the same query).

**Kiosk (`/timeclock`, a real screen — `FEATURES.timeclock` drops its `placeholder` flag and routes behind `KioskGuard` + `SetupGate` like `/scan`).** Jimmy: "Timeclock should be simple."

- **Finding a worker** (`lib/peopleMatch.ts`, over the synced `people` store). One always-focused box — the Scanning page's `.scan-input`, id `timeclock-input`, placeholder "Scan a badge or type a name" — takes a badge, an id, or a name. `matchPersonExact` resolves an RFID (zero-stripped and upper-cased through `displayRfid`, the same rule `scanMatch.ts` uses) or a person id, full or the eight-character short form (only when the value looks like hex, so a surname is never read as an id); it runs on **every keystroke**, so a badge selects its owner without waiting for the Enter a reader appends. Anything else goes to `searchPeople`, which filters as typed: every whitespace-separated term must be a case-insensitive prefix of a **distinct** name part (`first_name`, `last_name`, `preferred_name`, and each word of `display_name`), so "jim hen", "hen jim", "jimmy", "james henderson" and "henderson j" all find Jimmy Henderson while "tina tina" finds nobody. At most 8 results, ranked: a name typed out in full first, then fewer name parts, then alphabetically. Enter with one result selects it, with several does nothing (the list stays to be tapped), with none flashes the not-found color, plays the not-found sound, and says `No worker found for "{value}".` for 3 s.
- **Two states.** *Entry* is the box plus the tappable `.tc-result` rows (name, muted worker/account chips, the trimmed RFID). *Selected* is one `.tc-card` info blob: the avatar from the status endpoint's presigned `avatar_url` (falling back to a `.tc-avatar-fallback` circle of initials when it is null or the image fails), the name, and the portal's answer — "Clocked in for **2h 14m**" (counting up from `entry.started_at`, refreshed every 30 s) over "since {time} · {move} · {site}", or "Not clocked in" over "Last clock-out {time}", or "Checking the portal…" while the status is in flight.
- **One action.** A single 64px `.tc-action` button reading "Clock out" when they are on the clock and "Clock in" when they are not — never both, because the portal's answer already decides which is possible. Disabled while the status loads and while a punch is in flight ("Working…"). A `mini-btn` Cancel returns to entry, and so does 20 seconds of idle (reset on any interaction), so an unattended kiosk never sits on somebody's card.
- **Punching.** Clock-in sends `{serial, person_id, site_id, initiative_id}` with the site and move from Kiosk Setup; clock-out sends `{serial, person_id}`. Success flashes the Appearance tab's good color for `flash_ms`, plays the good sound, returns to entry and shows a 5 s `.tc-toast` — "Clocked in — {name}" or "Clocked out — {name} · 3h 12m". Failure flashes not-found, plays the not-found sound, and says why: `already_clocked_in` "They are already clocked in. Refreshing…" and `not_clocked_in` "They are not clocked in. Refreshing…" both re-read the status and stay on the card (the portal knows this worker's state better than the screen does); 423/`read_only_mode` "The portal is in read-only mode. Try again shortly."; `network` "Can't reach the portal. The punch was not recorded."; anything else "Couldn't record the punch ({code})."
- **No offline queue, deliberately.** Unlike scanning — whose outbox exists because a dock loses signal mid-shift — a punch that did not reach the API did not happen, and the screen says so rather than promising to send it later.
- **No punch history on the kiosk** (Jimmy, 2026-09-14): the confirmation toast is the only feedback; the portal's `time_entries` rows are the record. An earlier session-only recent list was removed.
- **No people synced** → "No people on this kiosk. Sync from Kiosk Setup." and the box disabled. The people list is read from IndexedDB on mount and rebuilt whenever a sync finishes (which is when the new name parts arrive).
- **Deferred**: an offline punch queue, break/lunch punches, photo capture at the punch, and any kiosk-side view of the day's hours.

## Implementation notes (2026-09-13)

Built on branch `kiosk-web` via `docs/superpowers/plans/2026-09-13-kiosk-web.md`. Migration head is **0061**. Deliberate deviations from the text above, all reviewed:

- **Pairing rate limit keys on the proxy-written address.** `deps.rate_limit_ip()` honors `X-Forwarded-For` only when the direct peer is loopback or private (Caddy on the same box) and then takes the RIGHTMOST entry, which the proxy appends; a public peer's header is ignored. The stored `ip_address` is the same value. The spec's "per IP" wording did not say which IP; the leftmost entry is attacker-controlled.
- **One-shot claim and approve/deny are conditional UPDATEs** (`WHERE status = 'approved'` / `'pending'`, rowcount-gated) so a retried poll or two approvers cannot mint two sessions. A claim denied at poll time (approver disabled or lost `kiosk:view`) is audited as `kiosk_pair_claim_denied`.
- **`client_viewer` test persona** needs a client anchor (`person_roles_client_scope_check`); `tests/test_auth_kiosk_login.py::_client_viewer` builds it.
