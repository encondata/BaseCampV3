# Kiosk (web mode): framework, sign-in, and shell

The kiosk is the scanning-floor face of ServerSherpa. It will eventually run in four modes (Web only, Laptop Mode, RFID Middleware, Device App). This spec builds the framework and the web mode's sign-in and shell only: a second app in `kiosk/` that mirrors the portal's look, signs in three ways (email and password, link with phone, move password placeholder), registers itself as a kiosk Device, and ships as its own Docker image on its own port. No scanning.

**Date:** 2026-09-13 · **Status:** approved (Jimmy, 2026-09-13: "looks good lets go") · **Branch:** `kiosk-web` (worktree off `reports`)

## Decisions already made

| Question | Decision |
|---|---|
| Code sharing | Own app in `kiosk/`; a Vite alias `@portal` reaches into `portal/src` for **stylesheets and React-free TypeScript only**. No npm workspace, no copied tokens. |
| Session model | Same cookie model as the portal (`ss_refresh` httpOnly cookie on the API host, in-memory access token). No body refresh tokens. |
| Who may sign in | New permission resource `kiosk` with one action `view`. Granted by default to developer, founder, super_admin, admin, staff, worker. |
| Kiosk identity | Each kiosk self-registers as a `Device` row (`device_type='kiosk'`) by serial, using the signed-in user's session. No pre-shared secret, no device token. Signing in registers the kiosk automatically (30 days, renewed when expired or within 7 days of expiring); anyone allowed to use the kiosk can do it. Register/Renew remain available in the portal, for registering ahead of time or renewing a kiosk nobody has signed into. |
| Pairing transport | Kiosk polls every 2 s while a code is showing. No WebSocket or SSE. |

### Runtime config (`src/lib/config.ts`)

Resolution order, read per call (never at module scope, same reason as the portal's `apiUrl()`):

1. `window.__KIOSK_CONFIG__.apiUrl` / `.portalUrl` (written by the Docker entrypoint, empty object in dev)
2. `import.meta.env.VITE_API_URL` / `VITE_PORTAL_URL`
3. `http://${window.location.hostname}:8000` / `http://${window.location.hostname}:5173`

`kioskVersion()` returns `import.meta.env.VITE_KIOSK_VERSION ?? package.json version` (Vite `define`).

### Identity (`src/lib/identity.ts`)

- `serial`: localStorage `ss.kiosk.serial`; generated once as `kiosk-web-<uuid4>`.
- `name`: localStorage `ss.kiosk.name`; default `Kiosk <last 4 hex of serial, uppercase>`; editable in Kiosk settings (trimmed, 1–80 chars, required).
- `getIdentity()` returns `{ serial, name }`. Both reads are wrapped in try/catch; if storage is unavailable the serial is regenerated per page load and settings shows a warning "This browser can't remember kiosk settings".

### Transport (`src/lib/api.ts`)

A compact re-implementation of the portal's session behavior, not an import of `portal/src/lib/api.ts` (that file drags in 500 lines of portal endpoints and its `apiUrl()` ignores runtime config). Same rules, stated once here so tests can pin them:

- Access token in a module variable only. Never in storage.
- `refreshSession()` is single-flight; `POST {api}/auth/refresh` with `credentials: 'include'`, no Authorization header; null on failure.
- `apiFetch(path, init)` pre-refreshes when the token is within 30 s of expiry, attaches `Authorization: Bearer`, and on 401 performs exactly one refresh and retry, then calls `notifySessionEnded()`.
- `loginRequest(email, password)` → `POST /auth/login` with body `{email, password, client: "kiosk"}`.
- `logoutRequest()` → `POST /auth/logout`, never throws.
- `createPairRequest({serial, name})`, `pollPair(code, pollToken)`, `heartbeatRequest(body)` — see API.
- `ApiError { status, code }` mirrors the portal's; `code` comes from `detail.code`, falling back to `'network'`.
- Types `SessionData`, `PersonOut`, `UiPreferences` are imported (type-only) from `@portal/lib/api`; `computeCan` from `@portal/lib/access`; `applyPreferences` from `@portal/lib/settings`.

### Auth context (`src/auth/KioskAuthContext.tsx`)

State: `status: 'loading' | 'authed' | 'anon'`, `person`, `perms`, `mustChangePassword`, `registration: RegistrationState | null` (from heartbeat), `sessionExpiresAt`.

- On mount: `refreshSession()`; if it returns a session → `adopt(session)`; else `anon`.
- `adopt(session)`: store token, `applyPreferences(session.preferences)`, set state, start the heartbeat.
- `login(email, password)` → `loginRequest` → `adopt`. `completePair(session)` → `adopt` (called by PairPanel).
- `logout()` → stop heartbeat, `logoutRequest`, clear state, `anon`.
- Subscribes to `onSessionEnded` → same as logout without the request.
- Subscribes to `installVisibilityRefresh` (refresh on tab focus), same as the portal.

### Heartbeat (`src/lib/heartbeat.ts`)

`startHeartbeat(onState, intervalMs, firstBeatIsSignIn)` posts immediately, then every 60 s, `{serial, name, mode, version}` to `POST /kiosk/heartbeat`; calls `onState(response.registration)` on success; on any failure (network, 423 read-only, 403) it keeps the last known state and retries next tick. Returns a `stop()` that clears the timer. It also re-posts immediately when the kiosk name changes (settings page calls `heartbeatNow()`). When `firstBeatIsSignIn` is true (set by `KioskAuthContext` only for the beat that follows `login()`/`completePair()`, never a cookie restore), that one beat only adds `sign_in: true` to the body — see the API's `### Heartbeat` section below for what the server does with it.

### Settings (2026-09-13)

Kiosk Setup renamed its route to `/setup` (still reachable signed in or out, still never behind `KioskGuard`); `/settings` is now a new tabbed **Settings** page, added as the last `FEATURES` tile (a sliders icon) and reachable signed in or out (see "This Kiosk moves off /setup" below) — never behind `KioskGuard` itself, though `Home`'s own `/` route still is.

A tab registry (`src/lib/settingsTabs.ts`) lists six sections in order: Appearance ("Theme, accent, and text size for this kiosk."), Sound ("Scan and alert sounds."), Devices ("Scanners, printers, and readers attached to this kiosk."), This Kiosk ("This kiosk's name, identity, and connection.", `anon: true`), Admin ("Kiosk administration.", `requires: 'admin'`), and Developer ("Diagnostics and developer tools.", `requires: 'developer'`). `visibleTabs(tabs, {isAdmin, isDeveloper, signedIn})` drops a tab whose `requires` the signed-in person lacks; signed out, only tabs carrying `anon` survive, which today means This Kiosk alone — **gating is by visibility only: a hidden tab is never rendered, never shown disabled**, and it carries no trace in the DOM (no "Admin"/"Developer" text for a worker, no "Appearance"/"Sound"/"Devices"/"Admin"/"Developer" text signed out). **Appearance tab — Flash duration (2026-09-14):** a third `.settings-row` below the two color pickers, label "Flash duration", hint "How long the screen flashes after a scan.", holding a range (`aria-label="Flash duration"`, min 100, max 2000, step 50) and a mono readout ("350 ms"). It writes `flash_ms` into the same kiosk-local `ss.kiosk.appearance` record (default **350**, clamped to 100–2000 on both read and write, so a hand-edited file can never hand the overlay a 0 ms flash), and `Scan.tsx` passes it to `flash(color, ms)` on both the match and the no-match path. `flash()`'s own default stays 350 for any caller that doesn't care.

**Sound tab (2026-09-14):** what this kiosk plays on a scan, kiosk-local in `ss.kiosk.sound` (`lib/sound.ts`, the same store/hook idiom as `appearance.ts`): `{good, not_found, volume}` where each choice is `{kind:'none'} | {kind:'builtin', id} | {kind:'upload', id}` and `volume` is 0–1 (default **0.8**, clamped). Defaults: good `builtin:chime`, not-found `builtin:buzz`. Built-ins are **synthesized with the Web Audio API**, not shipped as files — nothing to cache, nothing to 404 on an offline kiosk: `chime` (two rising sine notes, ~180 ms), `beep` (880 Hz square, 120 ms), `double_beep`, `buzz` (150 Hz sawtooth, 300 ms) and `bonk` (a descending sine). One `AudioContext` is created lazily on the first play and shared; the first play always follows a user gesture (a scan is a keypress), and `resume()` is called anyway for browsers that still start it suspended.

Uploads are the operator's own files, stored whole — `{id, name, type, size, blob, created_at}` — in IndexedDB **`sounds` (localDb v3**, keyPath `id`, deliberately outside `STORES` so "Clear local data" leaves them alone, like `outbox`). `addUploadedSound(file)` rejects `'not_audio'` for anything that isn't `audio/*` and `'too_large'` past **2 MB**; playback goes through an `HTMLAudioElement` over an object URL made once per id and revoked on removal, and `removeUploadedSound` resets any choice that pointed at the file to `none` so a scan never falls silent pointing at a row that no longer exists. `playScanSound('good' | 'not_found')` never throws — audio is feedback, never a gate.

The tab body (`components/SoundPanel.tsx`) is two `.settings-row`s, "Good scan sound" and "Not-found scan sound", each a native `<select>` (None, the built-ins, then the uploads under an "Uploaded" `optgroup`) with a "Play" `mini-btn` that previews the current choice — a native picker because the kiosk cannot import the portal's `ComboBox` across the two-Reacts boundary, and a sound is not something a label can describe. Then a "Volume" row (range 0–100 with a mono `%` readout) and an "Uploaded sounds" row: a file input (`accept="audio/*"`, helper text "MP3, WAV, or OGG up to 2 MB. Stored on this kiosk only.") over a `.sound-uploads` list of `.sound-upload-row`s (name, size in KB, Play, Remove). Rejections show inline as `.form-error`: "That file is too large (2 MB max)." / "That doesn't look like an audio file."

### Kiosk setup state (2026-09-13)

A global kiosk-local flag, `kiosk_setup_complete`, gates every launcher tile except Kiosk Setup and Settings until the kiosk has been set up. `src/lib/setupState.ts` mirrors `devMode.ts`'s store/hook shape: `KioskSetupState = 'incomplete' | 'complete' | 'failed'`, `SETUP_STATES` (the three values in that order), `readSetupState`/`writeSetupState`/`subscribeSetupState`/`useKioskSetupState` (localStorage key `ss.kiosk.setupState`, same try/catch idiom — a blocked or full store, or a garbage stored value, reads as `'incomplete'`), plus `isSetupComplete(state)` and `setupStateLabel(state)` ("Incomplete"/"Complete"/"Failed"). Storage is kiosk-local for now; a server-side Device field is deferred so the portal can show a kiosk's setup state too.

### Kiosk Setup wizard (2026-09-13)

The first real Kiosk Setup flow: a three-step wizard at `/setup` — pick a move, then which of that move's sites this kiosk is at, then a scan type — that stamps the kiosk's `Device` row server-side and marks `kiosk_setup_complete`. This replaces the earlier "Kiosk Setup is a placeholder" state (see "This Kiosk moves off /setup" above): `setup` drops `placeholder: true` in `features.ts` (it stays `alwaysAvailable`), and `/setup` moves from outside `KioskGuard` to inside it — setup writes a Device row on the signed-in person's behalf, so it now requires a signed-in person like every other feature route, while `featureAvailable` keeps it (and Settings) usable regardless of `kiosk_setup_complete`.

**Endpoints** (`api/src/serversherpa/api/routes/kiosk.py`, both `kiosk:view`):
- `GET /kiosk/setup-options` → `SetupOptionsOut {initiatives: [{id, name, status, status_label, client_name, scheduled_start, scheduled_end, source_site, destination_site}], scan_types: [{key, label, color}]}`. Initiatives are `initiative_type == 'move'`, `archived_at IS NULL`, and `status` **not** one of `HISTORICAL_INITIATIVE_STATUSES = ("completed", "cancelled")` — the terminal/historical keys from the `initiative` status vocabulary seeded in `migrations/versions/0016_initiatives.py` (the full vocabulary is `planned`/`scheduled`/`in_progress`/`on_hold`/`completed`/`cancelled`; everything but the last two is offered). This is broader than the portal's `DeviceEditModal.tsx`/`KioskDevices.tsx` move picker (planned/in_progress only) — the kiosk deliberately shows every move still in play, including `scheduled` and `on_hold`. `status_label` comes from that same vocabulary (falls back to the raw key if a value is ever missing); `client_name` is the move's `Client.name` (outer-joined on `client_id`, `null` when unset); `scheduled_start`/`scheduled_end` are the `Initiative` columns of the same names, as ISO strings (`null` when absent). `source_site`/`destination_site` are `{id, name} | null`, outer-joined from the move's `origin_site_id`/`destination_site_id` (either can be unset on a move that hasn't had its sites assigned yet). Ordering: in-progress moves first, then everything else, then by the earliest `scheduled_start` (nulls last), then by name. Scan types are active `asset` status values, ordered by `sort_order` then label. This endpoint exists because workers hold `kiosk:view` but not `initiatives:view` — they cannot call `/initiatives` directly, so the kiosk gets only the narrow slice it needs.
- `POST /kiosk/setup` body `KioskSetupIn {serial, initiative_id, site_id, scan_status}` → `KioskSetupOut {device_id, initiative_id, initiative_name, site_id, site_name, site_role, scan_status, scan_status_label}`. Finds the kiosk `Device` by serial (404 `device_not_found` if absent or not a kiosk), re-validates `initiative_id` against the same move/not-complete-or-historical/not-archived filter (422 `bad_initiative`) and `scan_status` against the active asset-status keys (422 `bad_scan_status`) — never trusts the options list a stale client cached — then checks `site_id` equals the chosen initiative's `origin_site_id` (`site_role = "source"`) or `destination_site_id` (`site_role = "destination"`), 422 `bad_site` otherwise. Not read-only exempt (it writes); 423 under read-only mode.

**Kiosk selection cache** (`src/lib/kioskSetup.ts`): `KioskSetupSelection {initiativeId, initiativeName, siteId, siteName, siteRole, scanStatus, scanLabel}`, kiosk-local, mirrors `devMode.ts`/`setupState.ts`'s store/hook shape (`readKioskSetup`/`writeKioskSetup`/`clearKioskSetup`/`subscribeKioskSetup`/`useKioskSetup`, localStorage key `ss.kiosk.setup`, same try/catch idiom). ### Local move data (2026-09-13)

After Kiosk Setup saves, the kiosk downloads the selected move's data into a browser-stored database so it can recognize an asset or a person without the API.

**Endpoints** (`routes/kiosk.py`, both `kiosk:view`, both one response with no paging — the roster is hundreds to a few thousand rows, the people list a few hundred):
- `GET /kiosk/sync/assets?initiative_id=<uuid>` → `KioskAssetsSyncOut {initiative_id, initiative_name, generated_at, assets: [KioskAssetOut]}`, where `KioskAssetOut = {id, asset_id, name, rfid, serial_number, make, model, make_model, label}`. `asset_id`, `make`, `model`, and `make_model` are computed straight from the asset/model columns (same join rule as `values.py`, `asset_id` = `Asset.legacy_id`, the human Asset ID; `rfid` is `Asset.rfid_tag`) — **not** read out of `label`, so an admin deactivating or deleting those placeholders (or the whole catalog) never breaks the endpoint's own fields. The roster is `initiative_assets` joined to `assets` (+ outer-joined `asset_models`), ordered by `legacy_id`; an asset not on the roster is never returned, but an *archived* asset that is still on the roster is returned like any other — roster membership is the truth here, not `archived_at`. `label` is the **label placeholder map** for that asset on that move, built by the label generator's own `labels/generate/values.py::placeholder_values()` over the *active* `label_placeholders` catalog minus `CONTAINER_KEYS` — i.e. up to `asset_id`, `asset_name`, `serial_number`, `make`, `model`, `make_model`, `source_raw`, `source_ru`, `source_site`, `destination_raw`, `destination_ru`, `destination_site`, `move_name`, `move_date`, and `{}` when the catalog is empty. Reusing the resolver (rather than re-deriving the fields here) is what guarantees an offline kiosk renders the same values a generated label carries, RU formatting (`U14`) and all. 404 `initiative_not_found`; 422 `bad_initiative` when the initiative is not a move.
- `GET /kiosk/sync/people` → `KioskPeopleSyncOut {generated_at, people: [{id, display_name, rfid_tag, is_worker, has_account}]}`: every `Person` with `archived_at IS NULL` that has a `worker_profiles` row **or** a `user_accounts` row, ordered by last then first name. A plain contact (neither) is never included. This is a literal reading of "has a profile/account", not "is currently usable": a disabled `UserAccount` or an inactive `WorkerProfile` is still listed (`has_account`/`is_worker` don't check `disabled_at` or an active flag) — worth revisiting once the kiosk grows a timeclock that needs to tell "can badge in" from "is in the directory".

**Privacy note**: `/kiosk/sync/people` puts names and RFID tags into storage on the kiosk itself, where they survive a reload. That is internal directory data — no email, phone, or address is sent — and both endpoints are gated on `kiosk:view` like the rest of the router, with the same scope caveat (no initiative/client scoping; see the setup-options note above). The docstrings say so at the code.

**IndexedDB** (`src/lib/localDb.ts`, no library, hand-rolled like the portal's `lib/labelCache.ts`): database `serversherpa-kiosk` v1, stores `assets` (keyPath `id`; indexes `rfid`, `asset_id`, `serial_number`), `people` (keyPath `id`; index `rfid_tag`), `meta` (keyPath `key`). API: `openDb()`, `replaceAll(store, rows)` (clear + put in ONE transaction, so the store is never observably empty and a failed write aborts the clear with it), `replaceAllMulti(entries, meta?)` (the same clear-then-put per store, but for *several* stores plus an optional meta row in ONE transaction — used to write `assets`, `people`, and the `sync` meta pointer together so a reader never sees them half-updated; resolves with each store's post-write `count()`, read inside the same transaction so it reflects what actually landed rather than the length of the array the caller passed in), `count(store)`, `getAll(store)`, `getByIndex(store, index, value)`, `readMeta(key)`, `writeMeta(key, value)` (stores `{...value, key}`), `clearDb()`, plus `closeDb()` for tests. Unlike `labelCache.ts`, failures are **not** swallowed: a missing `indexedDB`, a blocked open, or a failed transaction rejects, so `sync.ts` can show a real error instead of a kiosk that believes it has data. `withStores` explicitly `tx.abort()`s when its callback throws (some IDB failures, like `put()` on a row missing its keyPath, throw synchronously without the transaction ever hearing about it) so a mid-write failure always rolls back every store in that transaction, not just the write that failed; its completion promise also gets a no-op `.catch` at creation so an aborted transaction never surfaces as an `unhandledrejection`. One long-lived connection is cached (reopening per scan costs a round trip); a failed open is never cached.

**Sync** (`src/lib/sync.ts`): `runSync(initiativeId, initiativeName)` fetches both endpoints in parallel (`fetchAssetsSync`/`fetchPeopleSync` in `lib/api.ts`, through `apiFetch`) and only then writes `assets`, `people`, and the `meta` row `{key: 'sync', initiativeId, initiativeName, assets: n, people: n, syncedAt}` together via `replaceAllMulti`. The counts it reports (both in `meta` and in the status below) come from `count('assets')`/`count('people')` against the store after the write, not the fetched payloads' lengths. Status is a store/hook in `setupState.ts`'s shape — `useSyncStatus()` → `{phase: 'idle'|'running'|'done'|'error', assets?, people?, syncedAt?, error?}` — with `readSyncStatus`/`subscribeSyncStatus`/`resetSyncStatus` and `formatSyncedAt(iso)` (time only). **Failure semantics**: a fetch error reports the `ApiError` code, a database error reports `'storage'`; because the writes happen only after *both* fetches resolve, the previously cached rows are untouched either way, and the status keeps the counts it already had so the footer doesn't blink. `phase` is effectively persisted through the meta row: `hydrateSyncStatus()` (run once from `useSyncStatus`'s first mount) turns an existing `sync` row into `done` + counts, so a reloaded kiosk shows its local data without re-fetching. **Re-entrancy**: a module-level run counter means a newer `runSync` call always supersedes an older one still in flight — the older run checks its own run number against the counter before every status update and before writing anything, and once it is no longer current it writes nothing and reports nothing, so tapping "Sync again" mid-sync can never let a slow first run clobber the second run's result.

**Trigger and UI**: `KioskSetup.tsx`'s successful save calls `runSync(result.initiative_id, result.initiative_name)` **without awaiting** — the summary card appears at once and the download reports itself. Sync outcomes never touch `kiosk_setup_complete`: the kiosk is set up whether or not the copy downloaded. The summary card gains a `.sync-status` block: `idle` (before a first sync, or after the Developer tab cleared the database — otherwise a dead end) → "No move data on this kiosk yet." with a "Sync now" `mini-btn`; `running` → "Downloading move data…"; `done` → "Local data: {assets} assets · {people} people · synced {time}" with a "Sync again" `mini-btn`; `error` → "Couldn't download move data ({code})." with "Try again". `KioskShell`'s footer appends a `Data` item ("{assets} assets · {people} people") once counts exist (never "0 assets" on a kiosk that has never synced). The Developer tab (dev mode on, like the setup-state selector) gains a read-only "Local data" row with the same counts and time — "Nothing downloaded yet." before a first sync — and a "Clear local data" `mini-btn` that calls `clearDb()` then `resetSyncStatus()` on success; a `clearDb()` rejection instead shows an inline `.form-error` ("Couldn't clear local data.") and leaves the sync status exactly as it was.

**Testing**: `api/tests/test_kiosk_sync_api.py` (roster fields incl. the populated `label` map, off-roster asset absent, non-move 422, unknown 404, people include a worker and an account holder with RFID and exclude an archived person and a plain contact, worker 200 / client_viewer 403). Kiosk: `lib/localDb.test.ts` and `lib/sync.test.ts` (both `// @vitest-environment jsdom` + `import 'fake-indexeddb/auto'`, a fresh `IDBFactory` per test; `fake-indexeddb` is a new kiosk devDependency, as in the portal), plus the sync cases in `KioskSetup.test.tsx`, `KioskShell.test.tsx`, and `Settings.test.tsx`.

**Deferred**: delta sync (the roster is replaced wholesale every time), periodic/background refresh (the kiosk syncs on setup and on demand only), and any size limit or eviction policy for the local database.

### Scan ingest (2026-09-14)

The kiosk scans offline against its local copy of the move and pushes matched scans up in batches.

**`POST /kiosk/scans`** (`routes/kiosk.py`, `kiosk:view`, **not** read-only exempt — it writes). Body `KioskScanBatchIn {serial: str, scans: [KioskScanIn]}` with **1-100 scans** (0 or 101 → 422), where `KioskScanIn = {client_scan_id: uuid, scanned_value: str (1-200, stripped), scan_type: "rfid" | "barcode", scanned_at: datetime, asset_id: uuid | None, site_id: uuid | None, initiative_id: uuid | None, scan_status: str | None}`. Response `KioskScanBatchOut {accepted: [uuid], rejected: [{client_scan_id, code}]}`.

- **The kiosk sends only scans it already matched locally**, and its match rides along as `asset_id` — informational only. The server re-matches `scanned_value` from scratch in the scan-matching worker, so a stale local database can never mis-attribute a scan.
- **One `raw_scans` row per scan** — the same inbox `scans/worker.py` drains — with `device_id` = the kiosk Device's **name** (the reader/kiosk identity string that table has always carried), `operator_id` = the signed-in person, `source = "kiosk"`, and `match_attempted_at` left NULL, which is exactly what `run_once()` selects on. There is no workflow status on a raw scan: "fresh" *is* `match_attempted_at IS NULL`; `status` is the asset-status checkpoint (migration 0026).
- **Defaults from the Device.** `site_id`, `initiative_id`, and `scan_status` fall back to the kiosk's own setup (`devices.site_id` / `current_initiative_id` / `scan_status`) whenever the scan omits them, so the normal payload carries only the tag and the time. The checkpoint is written to **both** `status` (the FK'd column the matcher copies into `processed_scans` and status rules trigger on) and the new `scan_status` (what the device reported, verbatim).
- **Idempotent on `client_scan_id`.** The kiosk generates that uuid; ingest is `INSERT … ON CONFLICT DO NOTHING` against a partial unique index, so a batch retried because the kiosk never saw the response stores nothing new and reports every scan accepted again — the kiosk can clear its outbox on any 200.
- **Per-scan rejection, never per-batch.** A scan naming a site, move, checkpoint, or scan type the server does not know is rejected on its own with `bad_site` / `bad_initiative` / `bad_status` / `bad_scan_type` and the rest of the batch still lands; the response is 200 with both lists. One stale row must not cost a truckload of scans. A checkpoint only has to *exist* — a status deactivated mid-move keeps ingesting. `bad_scan_type` covers a `scan_type` the Literal accepts (`rfid`/`barcode`) but the `scan` vocabulary no longer has a row for — renamed or deleted after the kiosk cached it. The whole batch fails only on an unknown or non-kiosk serial (404 `device_not_found`), a malformed body (422), or read-only mode (423).
- **Audit**: one row per batch — `entity_type="device"`, `entity_id` = the device id, `action="kiosk_scans"`, `changes={"accepted": n, "rejected": n}` (not one per scan; `raw_scans` is itself the log). The batch also stamps `device.last_seen_at`, but not `updated_at` — that still means "this kiosk's configuration changed".
- **Migration `0063_raw_scan_kiosk_fields.py`** (`down_revision="0062"`) adds three nullable columns to `raw_scans`: `client_scan_id` (uuid, UNIQUE where not null — the idempotency key), `scan_status` (text, deliberately **un**-FK'd device-reported data, the counterpart of `devices.scan_status`), and `initiative_id` (FK `initiatives.id ON DELETE SET NULL` — deleting a move must not delete scan history). Downgrade drops all three.
- **No serial ownership proof, same as setup and heartbeat.** `kiosk:view` is all this endpoint checks — it does not confirm the caller is the kiosk named in `serial`, so any `kiosk:view` holder can post scans attributed to any kiosk (its site, move, and checkpoint ride along, or fall back to that device's own setup either way). `operator_id` is never spoofable this way: it is always the signed-in actor, not anything the body supplies. Accepted alongside the heartbeat's and setup's no-ownership notes (see "Implementation notes") until device tokens.

**Deferred**: the kiosk-side outbox and retry loop, unmatched-scan feedback to the kiosk, `manual` scan type over this endpoint (the vocabulary has it; the kiosk has no keyed-entry screen yet), and any per-kiosk rate limit.

### Scanning (2026-09-14)

The kiosk's working screen (`pages/Scan.tsx`, route `/scan`, behind `KioskGuard` + `SetupGate` like the other features). It scans against the move downloaded to this kiosk and pushes matched scans to `POST /kiosk/scans` out of a durable outbox.

**The input.** One `.scan-input` at the top, always focused: a barcode scanner is a keyboard, so a value typed while focus sits elsewhere is silently lost. Focus is taken on mount, taken back after every submit, and reclaimed by a `focusout`/`visibilitychange` handler whenever it lands somewhere that is not an `input`/`button`/`select`/`textarea`/`a` on the page — so an operator typing into some other control on the page (Settings, say) is not fought for focus. The toolbar's own one-shot buttons (Retry failed, Clear sent, Discard failed) are the deliberate exception to that: they take focus to be clicked, but hand it straight back to the scan input once their action resolves, rather than sitting on it like a sustained focus target would. Enter submits; an empty or whitespace-only Enter is a no-op. The input is disabled — with "No move data on this kiosk. Sync it from Kiosk Setup." — while the local `assets` store is empty.

**Matching** (`lib/scanMatch.ts`). `buildScanIndex(assets)` builds three maps and `matchScan` tries them in this order: **RFID** (keys and input both zero-stripped with `displayRfid` and upper-cased, so a handheld's unpadded read matches a fixed reader's EPC), then **asset ID**, then **serial number** (both trimmed + upper-cased). First row wins a duplicate key. `scanTypeFor` reports `rfid` for a tag match and `barcode` for everything else — the vocabulary's `manual` is not used (the kiosk cannot yet tell a typed serial from a scanned one).

**Flash and sound** (`lib/flash.ts`, `components/ScanFlash.tsx`, `lib/appearance.ts`, `lib/sound.ts`). Every scan plays the Sound tab's sound for its outcome alongside the flash — `playScanSound('good' | 'not_found')` right beside `flash(...)`, and it swallows its own failures so a kiosk with no audio device still records the scan. A match flashes the whole screen `good_scan`; no match flashes `not_found_scan`. Both last `flash_ms` (the Appearance tab's Flash duration). Both colors live in `ss.kiosk.appearance` as HSL channels, kiosk-local (the right green for a dark cage is not the right green for an office, and the color belongs to the screen rather than the signed-in account), defaults `good {h:150,s:60,l:45}` / `not-found {h:0,s:70,l:50}`. The Appearance tab edits them with an `HslPicker` each — swatch, three sliders, `hsl(...)` readout, Preview flash (which fires for the configured duration) — persisting on every drag. The overlay is rendered once in `KioskShell` (fixed, `inset:0`, click-through, above the shell), fades 0.85 → 0 over its duration, and holds a short solid flash instead under `prefers-reduced-motion`.

**Outbox** (`lib/outbox.ts`, IndexedDB store `outbox` in **localDb v2**, keyPath `client_scan_id`, index `status`). Row: `{client_scan_id, seq, scanned_value, scan_type, scanned_at, asset|null, matched, status, attempts, next_attempt_at?, last_error?, site_id, initiative_id, scan_status}`; the matched asset is denormalized so the list keeps reading right after a re-sync, and `seq` (a persisted monotonic counter) orders the list because a reader can fire twice inside one millisecond.

| | |
|---|---|
| Batching | a scan schedules a flush **500 ms** out; a scan inside that window rides along rather than pushing it back, so nothing waits longer than one window. Up to **100** rows per POST. |
| Retry | a thrown `ApiError` (network, 5xx, 423) returns the whole batch with `attempts+1` and `next_attempt_at = now + BACKOFF[attempts]`, `BACKOFF = [2000, 4000, 15000, 60000]`; the attempt after the 60 s wait is terminal (`failed`). A timer wakes the sender at the earliest due row. |
| Per scan | the response's `accepted` ids go green; a `rejected` id is `failed` with its code immediately (`bad_site`/`bad_initiative`/`bad_status` will never succeed), as is an id the response mentioned in neither list (`no_ack`). |
| Restart | `startSender()` resumes `queued`/`retrying` rows on mount; a row left `sending` by a reload resets to `queued` — ingest is idempotent on `client_scan_id`, so re-sending one that landed is free. A storage failure mid-flush (the write that marks a batch `sending`) gets the same recovery without a reload: `flushOutbox`'s catch resets that batch back to `queued` and reschedules — otherwise `dueRows` would never pick it up again. |

**What is NOT sent:** unmatched scans. They are stored `nomatch` and never leave the kiosk (the endpoint only takes scans the kiosk matched); they exist so the operator sees that the tag they waved resolved to nothing. `outbox` is deliberately outside `STORES`, so Developer › "Clear local data" empties the cached roster without discarding scans that have not reached the API. No match rows expire 120 s after they were scanned; the sender sweeps every 10 s.

**The list** (`.scan-list`, `.local-table` shape, newest first): Serial, Name, RFID (`displayRfid`, raw EPC on `title`), Make / Model, a mono time, and a status chip — "Sent" (green), "Queued"/"Sending"/"Retrying (n/4)" (yellow), "Failed: {code}" and "No match" (red). A `nomatch` row shows the raw scanned value in the Serial cell and a dash elsewhere. Above it, `.scan-counts` reads "{queued} queued · {accepted} sent · {failed} failed" with **Retry failed** (failed rows back to `queued`, attempts 0), **Clear sent** (drops accepted/nomatch only — a scan the portal never received is not "sent" and stays out of this button's reach), and **Discard failed** (shown once something has failed; confirms "Discard N failed scans? They were never received by the portal." before dropping them).

**Storage failures are surfaced, not swallowed.** A rejected `enqueueScan` — a scan that never made it into IndexedDB at all — shows a persistent `.scan-storage-error` alert ("Couldn't save the scan to this kiosk's storage — the last value was not recorded.") that clears the next time a write succeeds; a rejected `retryFailed`/`clearSent`/`discardFailed` shows "Couldn't update the scan list." the same way. Neither is left to surface as an unhandled rejection — the promise is always given both a success and a failure handler.

**Deferred**: manual `scan_type` (no keyed-entry mode), camera scanning, per-scan overrides of the kiosk's site/move/checkpoint, and any unmatched-scan lookup against the server.

### Pairing

Table `kiosk_pair_requests`:

| column | type | notes |
|---|---|---|
| id | uuid pk | |
| code | text unique | 8 chars, Crockford base32 alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`, `secrets.choice` |
| poll_token_hash | text | sha256 of the 32-byte urlsafe token returned once to the kiosk |
| serial | citext | kiosk serial |
| kiosk_name | text | |
| status | text | `pending` / `approved` / `denied` / `claimed`; expiry is derived from `expires_at`, never stored |
| approved_by | uuid null fk people | |
| ip_address | text null | creator IP |
| expires_at | timestamptz | created + 300 s |
| created_at | timestamptz | |
| updated_at | timestamptz | |

Index on `(ip_address, created_at)` for the rate limit and on `(serial)` for lookups (codes for the same serial are independent — see Implementation notes).

Endpoints:

- `POST /kiosk/pair` — **unauthenticated**. Body `PairCreateIn {serial: str (1–120), name: str (1–80)}`. Rules, in order: delete rows older than 24 h (cheap opportunistic cleanup); if `count(*) where ip_address = :ip and created_at > now() - 5 min >= 30` → 429 `pair_rate_limited`; insert; return `PairCreateOut {code, poll_token, link_url, expires_at}` where `link_url = f"{settings.portal_origin.rstrip('/')}/link/{code}"`. Read-only exempt (see below).
- `POST /kiosk/pair/{code}/poll` — **unauthenticated**. Body `{poll_token}`. 404 `pair_not_found` if no row; 403 `pair_forbidden` if the token hash mismatches (constant-time compare). Then: past `expires_at` → `{status: "expired"}`; `pending`/`denied`/`claimed` → `{status}` (`claimed` reported as `expired`, a one-shot code is spent); `approved` → mint a session for `approved_by` via `start_session(audit_action="login_pair")` with the kiosk's IP and user agent, set the refresh cookie, set status `claimed`, return `PairPollOut {status: "approved", session: SessionOut}`. If `approved_by`'s account is now disabled or has no `kiosk:view` → status `denied`. Read-only exempt.
- `GET /kiosk/pair/{code}` — requires `kiosk:view`. Returns `PairInfoOut {code, kiosk_name, serial, status, expires_at}` with `status` computed (`expired` when past). 404 when unknown.
- `POST /kiosk/pair/{code}/approve` — requires `kiosk:view`. 404 unknown; 409 `pair_not_pending` unless `pending` and unexpired. Sets `approved`, `approved_by = actor.person.id`, audits `kiosk_pair_approved` (entity `kiosk_pair`, changes `{serial, kiosk_name}`). 204. Read-only exempt (it is a sign-in).
- `POST /kiosk/pair/{code}/deny` — same gate; 409 unless pending; sets `denied`; audits `kiosk_pair_denied`; 204. Read-only exempt.

`deps.READ_ONLY_EXEMPT_PREFIXES` gains `"/kiosk/pair"`; `/kiosk/heartbeat` is **not** exempt (it writes a Device row and the kiosk tolerates failure).

Security notes, recorded so the review does not re-derive them: 40-bit codes with a 5-minute life and a per-IP creation cap; the code alone cannot claim a session because the poll token is required; approve is an authenticated action gated on the approver's own kiosk permission; the phone page names the kiosk and its serial so a user is not tricked into signing in a stranger's kiosk without seeing it; the session minted at claim time is a fresh family for the kiosk, so revoking it never touches the approver's phone session.

### Heartbeat

`POST /kiosk/heartbeat` — requires `kiosk:view`. Body `HeartbeatIn {serial: str, name: str, mode: Literal["web","laptop","pi","android","ios"], version: str | None, raw_info: dict = {}, sign_in: bool = False, login_method: Literal["password","link"] | None = None}`.

- Look up `Device` by `serial` (the existing partial unique index `devices_serial_uniq` covers this). None → insert `Device(device_type="kiosk", name, serial, sub_type=mode, version, raw_info, last_seen_at=now)`. Found with `device_type != "kiosk"` → 409 `serial_conflict`. Found kiosk → update `name`, `sub_type`, `version`, `raw_info` (merged, kiosk keys win), `last_seen_at`, `updated_at`.
- Returns `HeartbeatOut {device_id, name, registration: "ok"|"soon"|"expired"|"none", token_expires_at}` using the Kiosk Devices thresholds (7 days).
- Not audited (a heartbeat is telemetry); creation is audited once (`action="self_register"`, actor = signed-in person).
- **Sign-in auto-registers the kiosk and records who's on it.** `sign_in` is true only on the one heartbeat the kiosk sends right after a person signs in (password login or a completed pairing) — never on a cookie restore, never on a periodic tick. That beat carries `login_method` ("password" or "link") and the handler stamps `device.session_person_id = actor.person.id`, `device.session_login_method = login_method`, `device.session_started_at = now` — this is what the Kiosk Devices "Signed in"/"Login" columns read. Independently, when the kiosk's registration is not `"ok"` (i.e. `"none"`, `"expired"`, or `"soon"` — within 7 days of expiring), the same beat stamps `registered_at = now` and `token_expires_at = now + 30 days` (`KIOSK_AUTO_REGISTER_DAYS`, matching the portal's Register default) and writes an audit row exactly like the portal's Register action (`action="register"`, `entity_type="device"`) but `changes` carries an extra `source: "kiosk_sign_in"` key and the actor is the signed-in kiosk user. A sign-in on a kiosk that is already `"ok"` (more than 7 days left) changes nothing about the registration and audits nothing, but still records the new session.
- **`POST /kiosk/sign-out`** — requires `kiosk:view`. Body `{serial: str}`. Finds the kiosk `Device` by serial; if found and `session_person_id` is null or equal to the caller's person, clears `session_person_id`/`session_login_method`/`session_started_at` and stamps `updated_at`. Always 204 — an unknown serial or someone else's session is not an error, since the kiosk is about to drop its own token either way. Not read-only exempt (it writes; the kiosk ignores failures — see `signOutRequest`).
- **`DeviceItem` session fields**: `session_person_id`, `session_person_name` (built the same way as `Person.display_name`, via an outer join so a kiosk with no session reads null), `session_login_method`, `session_started_at`.
- **Kiosk Devices columns**: "Signed in" (the session person's name, or "—") and "Login" (a chip: "Password" / "Phone link" / "—"), both default-on, placed after Registration. A kiosk that vanishes without signing out (crash, unplugged, closed tab) keeps showing its last signed-in user until the next sign-in — there's no server-side timeout on the session fields. Stale detection is deferred; `last_seen_at` (already on the row) is the tell that the "Signed in" name may be stale.

### Timeclock (2026-09-14)

The kiosk punch clock: a worker walks up, is found by badge, RFID, or typed name against the synced people list, and is clocked in or out. The rows are ordinary `time_entries` — the portal's own time tracking — so a kiosk punch shows up in `GET /time/entries`, `/time/active`, the per-initiative summary and the approval queue like any other. All three endpoints require `kiosk:view`; the two POSTs write, so neither is read-only exempt.

- **`GET /kiosk/timeclock/{person_id}`** → `KioskTimeclockStatusOut {person: {id, display_name, first_name, last_name, preferred_name, avatar_url, rfid_tag}, clocked_in: bool, entry: {id, started_at, initiative_id, initiative_name, site_id, site_name} | null, last_entry: {...} | null}`. `entry` is the person's open entry (`clock_out_at IS NULL`) — the kiosk shows the avatar and counts up from `started_at`. `avatar_url` is presigned and short-lived (the same `presign_get(person.avatar_key)` the portal uses), null without an avatar. 404 `person_not_found` for an unknown **or archived** person (the people sync drops archived people too, so only a stale local cache asks).
- **`POST /kiosk/timeclock/clock-in`** — body `{serial, person_id, site_id?, initiative_id?, at?}`. Opens an entry with `clock_in_at = at or now`; `site_id` / `initiative_id` fall back to the kiosk Device's `site_id` / `current_initiative_id`, so the punch inherits the move and site from Kiosk Setup. Provenance: `source = "kiosk"` and `device_id` = the kiosk's Device (migration 0064). Audited `entity_type="time_entry"`, `action="kiosk_clock_in"`, `actor_id` = the signed-in operator, `changes = {person_id, site_id, initiative_id, device_id}`. Errors: 404 `device_not_found` / `person_not_found`; 409 `already_clocked_in` with the open entry's id in `detail.entry_id` (so the kiosk can offer "clock out" instead); 422 `bad_site` / `bad_initiative` when an id doesn't exist — 422 rather than 404 because a kiosk holding a stale setup is the likely cause. Returns the status shape, now clocked in.
- **`POST /kiosk/timeclock/clock-out`** — body `{serial, person_id, at?}`. Closes the open entry with `clock_out_at = at or now` and graduates it to `pending`, exactly as self-service clock-out does, so it lands in the timesheet-approval queue. 409 `not_clocked_in` when there is no open entry; 422 `bad_time` when `at` precedes `clock_in_at`. Audited `kiosk_clock_out` with the close diff plus `person_id` and `device_id`. Returns the status shape with `clocked_in: false`, `entry: null`, and `last_entry {id, started_at, ended_at, minutes}` so the kiosk can say "Clocked out after 3h 12m" without a second call.
- **`GET /kiosk/sync/people`** additionally carries `first_name`, `last_name` and `preferred_name` per person, so the kiosk can match a typed name in any order without re-splitting `display_name`.
- **Any kiosk user can punch any worker.** Unlike `/time/clock-in`, which acts strictly on the caller's own person id, these act on ANOTHER person and check nothing but `kiosk:view` — deliberate, and the same accepted risk as the rest of this router (no serial ownership proof either). It matches the physical situation: one shared screen on a dock, one person tapping it for whoever is in front of them. Every punch is attributable — the audit row's actor is the signed-in operator, never the punched worker, and `device_id` names the kiosk.
- **Shared entry mechanics.** `services/timeclock.py` owns the rules both paths must agree on: one open entry per person (the advisory pre-check plus the `one_open_entry_per_person` partial unique index, surfaced as a clean 409 from a savepointed flush), closing into `pending`, and worked minutes as span-minus-break, never negative. `routes/time.py` was moved onto it with no behavior change.

**Kiosk (`/timeclock`, a real screen — `FEATURES.timeclock` drops its `placeholder` flag and routes behind `KioskGuard` + `SetupGate` like `/scan`).** Jimmy: "Timeclock should be simple."

- **Finding a worker** (`lib/peopleMatch.ts`, over the synced `people` store). One always-focused box — the Scanning page's `.scan-input`, id `timeclock-input`, placeholder "Scan a badge or type a name" — takes a badge, an id, or a name. `matchPersonExact` resolves an RFID (zero-stripped and upper-cased through `displayRfid`, the same rule `scanMatch.ts` uses) or a person id, full or the eight-character short form (only when the value looks like hex, so a surname is never read as an id); it runs on **every keystroke**, so a badge selects its owner without waiting for the Enter a reader appends. Anything else goes to `searchPeople`, which filters as typed: every whitespace-separated term must be a case-insensitive prefix of a **distinct** name part (`first_name`, `last_name`, `preferred_name`, and each word of `display_name`), so "jim hen", "hen jim", "jimmy", "james henderson" and "henderson j" all find Jimmy Henderson while "tina tina" finds nobody. At most 8 results, ranked: a name typed out in full first, then fewer name parts, then alphabetically. Enter with one result selects it, with several does nothing (the list stays to be tapped), with none flashes the not-found color, plays the not-found sound, and says `No worker found for "{value}".` for 3 s.
- **Two states.** *Entry* is the box plus the tappable `.tc-result` rows (name, muted worker/account chips, the trimmed RFID). *Selected* is one `.tc-card` info blob: the avatar from the status endpoint's presigned `avatar_url` (falling back to a `.tc-avatar-fallback` circle of initials when it is null or the image fails), the name, and the portal's answer — "Clocked in for **2h 14m**" (counting up from `entry.started_at`, refreshed every 30 s) over "since {time} · {move} · {site}", or "Not clocked in" over "Last clock-out {time}", or "Checking the portal…" while the status is in flight.
- **One action.** A single 64px `.tc-action` button reading "Clock out" when they are on the clock and "Clock in" when they are not — never both, because the portal's answer already decides which is possible. Disabled while the status loads and while a punch is in flight ("Working…"). A `mini-btn` Cancel returns to entry, and so does 20 seconds of idle (reset on any interaction), so an unattended kiosk never sits on somebody's card.
- **Punching.** Clock-in sends `{serial, person_id, site_id, initiative_id}` with the site and move from Kiosk Setup; clock-out sends `{serial, person_id}`. Success flashes the Appearance tab's good color for `flash_ms`, plays the good sound, returns to entry and shows a 5 s `.tc-toast` — "Clocked in — {name}" or "Clocked out — {name} · 3h 12m". Failure flashes not-found, plays the not-found sound, and says why: `already_clocked_in` "They are already clocked in. Refreshing…" and `not_clocked_in` "They are not clocked in. Refreshing…" both re-read the status and stay on the card (the portal knows this worker's state better than the screen does); 423/`read_only_mode` "The portal is in read-only mode. Try again shortly."; `network` "Can't reach the portal. The punch was not recorded."; anything else "Couldn't record the punch ({code})."
- **No offline queue, deliberately.** Unlike scanning — whose outbox exists because a dock loses signal mid-shift — a punch that did not reach the API did not happen, and the screen says so rather than promising to send it later.
- **No punch history on the kiosk** (Jimmy, 2026-09-14): the confirmation toast is the only feedback; the portal's `time_entries` rows are the record. An earlier session-only recent list was removed.
- **No people synced** → "No people on this kiosk. Sync from Kiosk Setup." and the box disabled. The people list is read from IndexedDB on mount and rebuilt whenever a sync finishes (which is when the new name parts arrive).
- **Deferred**: an offline punch queue, break/lunch punches, photo capture at the punch, and any kiosk-side view of the day's hours.

## Implementation notes (2026-09-13)

Built on branch `kiosk-web` via `docs/superpowers/plans/2026-09-13-kiosk-web.md`. Migration head is **0061**. Deliberate deviations from the text above, all reviewed:

- **Pairing rate limit keys on the proxy-written address.** `deps.rate_limit_ip()` honors `X-Forwarded-For` only when the direct peer is loopback or private (Caddy on the same box) and then takes the RIGHTMOST entry, which the proxy appends; a public peer's header is ignored. The stored `ip_address` is the same value. The spec's "per IP" wording did not say which IP; the leftmost entry is attacker-controlled.
- **One-shot claim and approve/deny are conditional UPDATEs** (`WHERE status = 'approved'` / `'pending'`, rowcount-gated) so a retried poll or two approvers cannot mint two sessions. A claim denied at poll time (approver disabled or lost `kiosk:view`) is audited as `kiosk_pair_claim_denied`.
- **`client_viewer` test persona** needs a client anchor (`person_roles_client_scope_check`); `tests/test_auth_kiosk_login.py::_client_viewer` builds it.
- **Kiosk toolchain:** vitest is pinned `^3.2.4` (vitest 4 requires vite 6+; the portal only gets away with vitest 4 because npm nested a second vite under it). `test.environment` is `node` by default and every DOM test carries `// @vitest-environment jsdom`. `main.tsx` uses StrictMode; `PairPanel` guards its mount request with a generation counter so dev mode mints one code.
- **Docker image installs only the kiosk's packages.** `npm ci --prefix portal` inside the image fails on the portal lockfile's peer conflict, and nothing in the image needs it: `vite.config.ts` dedupes `gsap` to the kiosk's copy and portal type imports are erased. The image runs `npm run build:bundle` (`vite build`); type-checking stays in `npm run build` outside the image.
- **Shell CSS:** `.portal-shell.kiosk-shell` (doubled selector) overrides the portal shell's nav+main grid, `height: 100vh` and `overflow: hidden`; the kiosk lays out as one column with a scrolling `.kiosk-main`. The login pane is light (paper), so the method switch and text code use the pane's dark-text tokens with the active pill inverted.
- **Class names:** inside the shell the kiosk uses the portal's `btn-solid` / `mini-btn` (there is no `.btn`/`.btn-ghost` outside the login theme). Settings shows an inline "Kiosk name saved." notice rather than a toast (the portal's ToastHost is a React component). `KioskBanners` fetches `/system/status` itself for the same reason.
- **`/link/:code` load errors:** 404 / `pair_not_found` / `pair_not_pending` show the expired copy; any other failure shows "Something went wrong. Try again." with a Retry that reloads.
- **Retire-on-create dropped:** an unauthenticated caller who knew a kiosk's serial could keep denying its code; several live codes per serial are harmless because codes are one-shot and expire in 5 minutes.
- **Heartbeat has no serial ownership proof:** any `kiosk:view` holder can rename any kiosk by posting its serial in a heartbeat, and by the same token can also claim another kiosk's "Signed in" cell for themselves by posting its serial with `sign_in: true` (never a third party — the audit names the real, signed-in actor). Accepted for this pass — device tokens/enrollment secrets are out of scope (see "Out of scope").
- **`/kiosk/setup-options` and `POST /kiosk/setup` are gated on `kiosk:view` only, ignore initiative scoping** (any kiosk user sees every active move and its sites), **and let any kiosk user re-point ANY kiosk by serial** — accepted alongside the heartbeat's no-ownership note above until device tokens; the portal's equivalent needs `scanning_hardware:change`. Also note: the portal may set a kiosk's site outside the move's origin/destination, which the wizard's `POST /kiosk/setup` would reject (`bad_site`) — the two paths are not fully interchangeable.
- **De-register in the portal is undone by the next kiosk sign-in.** Registration is a lifecycle marker, not a gate — it doesn't block anything — so a kiosk someone de-registered in the portal re-registers itself the moment the next person signs in there; the re-registration is audited with `source: "kiosk_sign_in"` like any other auto-registration.
